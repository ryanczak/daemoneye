# Bug 1 on phase-01: `run_costs` does not re-sort merged groups after combining segments — non-day groupings return incorrectly ordered output

**Severity:** major
**Status:** open
**Filed:** 2026-07-09

## What's wrong

`run_costs` in `src/cli/commands/costs.rs:255-289` opens every segment
returned by `event_segment_paths_between`, calls the existing
`aggregate_costs` on each segment individually (which sorts *that segment's*
groups internally — descending by `total_cost_usd` for non-`Day` groupings,
per `aggregate_costs` at `src/cli/commands/costs.rs:189-200`), and then
merges the per-segment summaries by appending/updating `summary.groups` in
place:

```rust
for seg_group in seg_summary.groups {
    if let Some(existing) = summary.groups.iter_mut().find(|g| g.key == seg_group.key) {
        existing.calls += seg_group.calls;
        ...
        existing.total_cost_usd += seg_group.total_cost_usd;
        ...
    } else {
        summary.groups.push(seg_group);
    }
}
```

The merged `summary.groups` vector is never re-sorted after all segments are
combined. Each group keeps the position it was first inserted at (i.e. its
sort rank *within whichever segment it first appeared in*), not its rank by
merged total.

Reproduced against the real compiled binary (`target/debug/daemoneye`), not
a unit-test fake — two dated segments, `--by agent`:

- `events-20260101.jsonl`: `high` cost 100.0, `low` cost 1.0 (segment-local
  sort: `high` first).
- `events-20260102.jsonl`: `low` cost 200.0 (segment-local: `low` only).

```
$ target/debug/daemoneye costs --since 2026-01-01 --until 2026-01-03 --by agent --json
{
  "groups": [
    { "key": "high", "calls": 1, "total_cost_usd": 100.0, ... },
    { "key": "low",  "calls": 2, "total_cost_usd": 201.0, ... }
  ],
  ...
}
```

`low`'s merged total (201.0) is greater than `high`'s (100.0), but `high` is
listed first. The output claims descending-by-cost order (that's what
`--by agent` has always meant) but is not actually sorted that way once more
than one segment contributes to a group.

This is a real regression introduced by the phase 01 migration: before this
phase, `run_costs` read one file and called `aggregate_costs` once, so the
internal sort was always correct. The multi-segment merge added by this
phase broke that guarantee for every `GroupBy` variant except `Day` (`Day`
happens to look right by coincidence in common cases because segment
insertion order tracks date order, but `Agent` / `Provider` / `Model` /
`Session` grouping has no such relationship to segment order).

No test caught this. The only tests exercising `run_costs` with a non-`Day`
`GroupBy` (`cli_costs_json_output_matches_schema`, `--by agent`) use a
single segment and assert only `result.is_ok()` — they don't inspect
`summary.groups` at all, so they would pass even with this bug present (or
with the aggregation logic returning nonsense). See bug-01-3 for the related
test-coverage gap.

## What should happen

Phase doc acceptance criterion: "`daemoneye costs` output over a date range
spanning legacy + dated segments matches the pre-phase output for the same
fixture set." Pre-phase behavior for any grouping was always sorted by the
documented order (descending cost for non-`Day`, ascending key for `Day`).
Multi-segment output must match that same order, regardless of which
segment(s) a group's events happened to land in.

## How to fix

After the merge loop in `run_costs` (`src/cli/commands/costs.rs`, right
before the `if json { ... }` block), re-apply the same sort `aggregate_costs`
uses:

```rust
match group_by {
    GroupBy::Day => summary.groups.sort_by(|a, b| a.key.cmp(&b.key)),
    _ => summary.groups.sort_by(|a, b| {
        b.total_cost_usd
            .partial_cmp(&a.total_cost_usd)
            .unwrap_or(std::cmp::Ordering::Equal)
    }),
}
```

(Consider extracting this into a shared `sort_groups(&mut Vec<CostGroup>, GroupBy)`
helper called from both `aggregate_costs` and `run_costs` to avoid the
duplicated match arms — optional, not required to fix the bug.)
