# Bug 1 on phase-09: boundary-safe-reload tests are vacuous (no tool_results in fixtures)

**Severity:** major
**Status:** closed 2026-07-31 — verified fixed against the code during M7 scoping; see phase-02 for the gate that now prevents this drift.
**Filed:** 2026-07-16

## What's wrong

The two tests that are supposed to verify §4 (boundary-safe reload) do not
exercise it at all — they pass even when the entire boundary/repair logic is
deleted.

Both `read_session_file_lands_on_clean_boundary` and
`read_session_file_repairs_when_no_boundary` (in `src/daemon/session.rs` test
module) build their fixtures with the plain `make_msg(role, content)` helper:

```rust
let msgs: Vec<Message> = vec![
    make_msg("user", "hello"),
    make_msg("assistant", "thinking"),
    make_msg("user", "tool result 1"),   // <-- NOT a tool_results message
    make_msg("user", "tool result 2"),
    make_msg("user", "tool result 3"),
];
```

`make_msg` sets `tool_results: None` and `tool_calls: None` (`session.rs`, test
module). So these are ordinary user messages merely *named* "tool result N".
Consequences:

- `assert_no_orphan_tool_results(&result)` is **trivially true** — no message
  in the fixture has a `tool_results` field, so no orphan is possible regardless
  of what `read_session_file` returns.
- Every message is already a clean boundary (`user` without `tool_results`), so
  `next_clean_turn_start` returns immediately and `repair_tail_head` is never
  reached. The `read_session_file_repairs_when_no_boundary` test never enters
  the repair branch it claims to cover.

**Proof (mutation test):** replacing the whole boundary body of
`read_session_file` with the raw slice `msgs[msgs.len() - cap..].to_vec()`
(no `next_clean_turn_start`, no `repair_tail_head`) leaves **both tests
passing** (`test result: ok. 2 passed`). A test that passes against gutted
code-under-test verifies nothing.

The §4 production code itself is correct and complete (`session.rs`
`read_session_file` advances to `next_clean_turn_start`, else `repair_tail_head`)
— only the *tests* are fake.

## What should happen

Two acceptance criteria require real coverage (phase doc §Acceptance):

- "Reload of a history whose natural tail slice starts on a **tool_results**
  message produces an orphan-free vec."
- "A reload where **NO clean boundary** exists in the tail is repaired, not
  returned raw (negative case)."

Both fixtures must contain actual `tool_calls`/`tool_results` messages, and each
test must fail if the boundary/repair logic is removed.

## How to fix

In `src/daemon/session.rs`'s test module, add fixtures with real tool messages
(pattern already used in `digest.rs:544-566`):

```rust
fn tool_call_msg(id: &str) -> Message {
    Message {
        role: "assistant".to_string(),
        content: "calling".to_string(),
        tool_calls: Some(vec![ToolCall {
            id: id.to_string(),
            name: "read_file".to_string(),
            arguments: "{}".to_string(),
            thought_signature: None,
        }]),
        tool_results: None,
        turn: None,
    }
}

fn tool_result_msg(id: &str) -> Message {
    Message {
        role: "user".to_string(),
        content: String::new(),
        tool_calls: None,
        tool_results: Some(vec![ToolResult {
            tool_call_id: id.to_string(),
            tool_name: "read_file".to_string(),
            content: "ok".to_string(),
        }]),
        turn: None,
    }
}
```

(Import `ToolCall`/`ToolResult` in the test module — `use crate::ai::{ToolCall,
ToolResult};` or the crate path they live at, `src/ai/types/wire.rs`.)

- **`read_session_file_lands_on_clean_boundary`:** build a history whose raw
  `msgs.len() - cap` slice-start lands on a `tool_result_msg` (its producing
  `tool_call_msg` dropped by the cap), followed later by a clean
  `make_msg("user", …)`. Assert the returned vec starts at that clean user
  message (the orphaned `tool_results` is excluded) and
  `assert_no_orphan_tool_results` holds.
- **`read_session_file_repairs_when_no_boundary`:** build a tail where the last
  `cap` messages are ALL `tool_result_msg` (no clean `user`-without-tool_results
  boundary anywhere in the slice), so `next_clean_turn_start` returns `None`.
  Assert the result went through `repair_tail_head` (leading orphaned
  `tool_results` stripped) and `assert_no_orphan_tool_results` holds.

Keep the three already-good tests (`meta_roundtrip`, `meta_corrupt_returns_none`,
`entry_recreation_seeds_from_meta`) as-is.
