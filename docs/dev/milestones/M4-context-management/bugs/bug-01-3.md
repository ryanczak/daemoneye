# Bug 3 on phase-01: `search_events_in_segments` can return the wrong (oldest, not newest) lines within the current segment, and has zero test coverage

**Severity:** minor
**Status:** verified
**Filed:** 2026-07-09
**Resolved:** 2026-07-09 (session takeover)

## Resolution

`search_events_in_segments` (`src/search.rs`) now reads each segment's valid
lines into a buffer and takes only the *tail* of each (newest lines) to fill the
remaining `EVENTS_TAIL_LINES` cap, iterating segments newest-first, then restores
oldest-first order for display — restoring the pre-phase "last N lines" contract
even when a single day's segment exceeds the cap. Covered by
`search_events_returns_tail_not_head_when_segment_exceeds_cap`. (The executor's
draft of this test queried the raw-JSON form `"idx":N`; `search_events` matches
the `json_to_readable` `key=value` rendering, so the query was corrected to
`idx=N` — this mismatch is what the executor looped on during its run.)

## What's wrong

`search_events_in_segments` (`src/search.rs:173-224`, replacing the old
`search_events`) is supposed to preserve the pre-phase contract of searching
"the last `EVENTS_TAIL_LINES` (10,000) lines" of event history (see the
phase doc's Current state item 5 and Spec item 4.5).

The implementation iterates segments newest-first (`event_segment_paths_between(None, None)`
reversed), and within each segment reads lines **in file order (oldest to
newest within that file)**, stopping once the running total hits the
10,000-line cap:

```rust
for path in &all_paths {                 // newest segment first
    ...
    for line_result in reader.lines() {  // oldest-to-newest WITHIN this file
        ...
        collected.push((readable, global_line_num, segment_name.clone()));
        if collected.len() >= EVENTS_TAIL_LINES {
            break;
        }
    }
    if collected.len() >= EVENTS_TAIL_LINES { break; }
}
```

If the newest (today's, still being appended) segment alone has more than
10,000 lines, this collects the **first** 10,000 lines written to that
segment today (the oldest events of the day) and never reaches the most
recent ones — the opposite of "last N lines." The old implementation read
the whole file and sliced the true tail (`all_lines[start..]`), so this is a
behavioral regression for any single day with heavy event volume.

Separately: there is no test at all for `search_events_in_segments` after
the migration. `src/search.rs`'s existing test module
(`search_finds_match_in_runbooks`, `search_returns_empty_for_no_match`,
`search_respects_kind_filter`) only exercises `kind="runbooks"` /
`"scripts"`; none set `kind="events"` or `"all"` and write event fixtures.
The phase doc's own Test plan section doesn't list a search.rs test either,
but STANDARDS §3.1 ("every new public function with non-trivial behavior:
at least one unit test covering the happy path, plus boundary cases") still
applies to this migrated function, and it's exactly the kind of
order/cap-sensitive logic that silently regresses without one.

## What should happen

Per the phase doc: "different shape: it wants the last 10_000 lines.
Implement by iterating `event_segment_paths_between(None, None)` newest
first, collecting lines until the cap, then restoring oldest-first order for
display." The intent (matching pre-phase behavior) is the true last 10,000
lines across all segments combined, not "first 10,000 lines of whichever
segment happens to be newest."

## How to fix

Within each segment (especially the newest one, which is the one most
likely to exceed the cap in a single file), read the file's lines into a
buffer and take the tail (`lines.len().saturating_sub(remaining_cap)..`)
before appending to `collected`, mirroring what the old single-file
implementation did — or read each file's lines in reverse. Then add:

- A test with a single (newest) segment containing more than
  `EVENTS_TAIL_LINES` lines, asserting the returned matches come from the
  tail (most recent) lines, not the head.
- A test with two segments (older + newer) asserting cross-segment
  oldest-first display order is preserved for the common (under-cap) case.
