# Bug 2 on phase-05: `handle_ask` panics if the entry is evicted between the probe and the insert

**Severity:** major
**Status:** open
**Filed:** 2026-10-19

## What's wrong

`src/daemon/server/ask.rs`, `handle_ask`, after the bug-05-1 fix:

```rust
let entry = store
    .get_mut(id.as_str())
    .expect("the probe or the insert above guarantees the entry exists");
```

The guarantee does not hold. The probe and the insert run under **two**
separate `with_sessions` calls, and the lock is released between them.
When the probe finds the entry present, nothing is built (`built` is
`None`). If `cleanup_pass`, which runs concurrently from the daemon's
background loop in `src/daemon/mod.rs`, evicts that idle entry inside the
gap, `get_mut` returns `None` and the ask task panics.

This is also a new production `expect`: `ask.rs` had none before this
phase.

## What should happen

There is no panic path. An entry that disappears between the probe and the
insert is a rare race. It is handled without `unwrap`/`expect`, and
without file I/O under the lock (bug-05-1 still holds).

## Root cause

The bounce note's worked example said the closure "continues with
`store.get_mut(id)…` (the entry now exists)". That is true only when this
task inserted the entry, not when the probe found it present.
