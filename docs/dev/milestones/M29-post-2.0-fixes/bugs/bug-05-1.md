# Bug 1 on phase-05: `from_disk` reads the disk while holding the session-store lock

**Severity:** major
**Status:** open
**Filed:** 2026-10-19

## What's wrong

Both resident-entry creation sites build the entry **inside** the
`with_sessions` closure:

- `src/daemon/server/chat_presence.rs`, in `handle_chat_attach`:
  `with_sessions(&sessions, |store| { store.entry(…).or_insert_with(|| SessionEntry::from_disk(&session_id)); })`
- `src/daemon/server/ask.rs`, in `handle_ask`:
  `with_sessions(sessions, |store| { let entry = store.entry(id.clone()).or_insert_with(|| SessionEntry::from_disk(id)); … })`

`SessionEntry::from_disk` reads `<id>.jsonl` (the whole history) and the
meta file. `or_insert_with` runs it while the `SessionStore` mutex is held.

The attach site's own comment says the opposite: "`from_disk` reads files,
so it must run outside the store lock — the build-then-insert form". The
code is not that form.

## What should happen

No file I/O while the `SessionStore` lock is held. This is the rule the
pre-phase `handle_ask` followed: it read the meta outside the lock, and a
comment said a file read "must not run inside a critical section".

## Root cause

The spec's gotcha allowed building the entry "outside or inside a single
`with_sessions` closure". Inside is wrong, because the closure **is** the
critical section. It is a std `Mutex` held on an async runtime thread, so
a large history blocks every other session operation for the length of
the read.

## Definition of done

- [ ] In both production sites (outside `#[cfg(test)]`),
      `or_insert_with(|| SessionEntry::from_disk` no longer appears. The
      end-to-end line `in_lock_builds=0` replaces today's `2`.
- [ ] `from_disk` runs before `with_sessions`, and only when a
      `contains_key` probe says the entry is absent. The insert keeps an
      entry that appeared in the meantime.
- [ ] `cargo test` ⇒ `passed=2425`, **not** 2426. The fix adds no test.
- [ ] The comment at the attach site describes what the code does.
