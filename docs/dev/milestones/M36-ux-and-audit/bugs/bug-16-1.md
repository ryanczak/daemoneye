# Bug 1 on phase-16: an interrupted background run's completion message also says it "may still be running"

**Severity:** major
**Status:** fixed (0789a2d8, architect takeover, approved 2026-11-07)
**Filed:** 2026-11-07

## What's wrong

`await_and_notify` (`src/daemon/executor/bg_shell.rs`, about line 340)
reduces an interrupted outcome, `CommandTimedOut { interrupted: Some(o) }`,
to `Err(String)`. The string says the command was interrupted with Ctrl-C
and exited with code N.

`completion_message` then gets that `Err` and always appends its generic
`Err` body (about line 280):

```
The command may still be running in shell {shell_id} — do not assume it
failed outright; retrying could double-apply its effect. ...
```

So the `[Background Task Completed]` message the model gets for an
interrupted run reads, in full:

```
Background command `…` (run …, shell sN) did not complete: … timed out and
was interrupted with Ctrl-C; it then exited with code 130. read_shell(shell:
"sN") reads it..
The command may still be running in shell sN — do not assume it failed
outright; retrying could double-apply its effect. …
```

It says the command exited with a real code, then that it may still be
running. It also ends the first sentence with two full stops. No test
covers this path.

## What should happen

Behaviour 6 of the phase doc says the completion message for an interrupted
background run states that it was interrupted after its timeout, gives its
exit code, and says that `read_shell(shell: "<id>")` reads it.

An outcome with a real exit code means nothing is still running. The
"may still be running … double-apply" caveat is the exact wrong guidance
that B10's foreground branch (`shell_run_error_text`, the `Some` form) was
written to remove. The background message must match it.

Every other `Err` keeps today's text unchanged: a dropped handle, a
`CommandTimedOut` with `interrupted: None`, or a plain error.

## Root cause

`await_and_notify` passes `completion_message` a
`Result<CommandOutcome, String>`. That type has no way to tell an
interrupted-with-outcome run apart from a failed one. So the
`completion_message` `Err` arm cannot know that the caveat does not apply.
The spec's § Pinned design C said "`completion_message` and its signature
are unchanged". That was the architect's error.

## Definition of done

- [ ] A new test, `bg_interrupted_completion_names_the_exit_not_still_running`,
      in `bg_shell.rs`'s tests. It drives `await_and_notify` with a
      hand-built `CommandHandle`. Its `outcome` is a `oneshot::Receiver`
      whose sender already sent
      `Err(CommandTimedOut { interrupted: Some(<outcome with exit_code 130>), .. }.into())`.
      Its `nonce` is any `Nonce::new()`. The test then reads the pushed
      `[Background Task Completed]` message from the session store, as
      `bg_notify_pushes_a_completion_message_carrying_the_real_exit_code`
      does. The test asserts all of the following:
      - the message contains `130`, `Ctrl-C` and `read_shell(shell: "<id>")`;
      - the message does **not** contain `may still be running`;
      - the message does **not** contain `..`.
      Against the current tree this test fails on the
      `may still be running` assertion.
- [ ] The existing `bg_` tests pass, unmodified. That includes the one
      that checks a failed outcome still carries the caveat.
- [ ] `cargo test` reports **2770** passed, 0 failed (2769 today, plus
      this one test).
