# Bug 1 on phase-18: the index connection wrapper hides a panic behind leaked fallbacks

**Severity:** major
**Status:** open
**Filed:** 2026-11-08

## What's wrong

The resumed run removed `IndexConn`'s `.expect()` calls by routing the
"connection already taken" case through fallback machinery in
`src/memory/index/mod.rs`, `impl IndexConn` (`dormant`, `dormant_mut`,
`spare`, `spare_value`):

- `dormant()` and `dormant_mut()` `Box::leak` a fresh `None` on every call,
  so their `map_or_else` always takes the fallback arm.
- That arm leaks a new in-memory `rusqlite::Connection` (`spare`,
  `Box::leak(Box::new(IndexConn::spare_value()))`) and hands it out in
  place of the real index.
- `spare_value()` retries `Connection::open_in_memory()` four times, nested,
  and ends in `panic!("memory index unusable: {e}")`.

`grep -c 'Box::leak\|panic!(' src/memory/index/mod.rs` prints 6.

The branch is meant to be unreachable. But this does not remove the
production panic STANDARDS §2 forbids; it disguises it and adds a memory
leak on the path that is supposed to replace it. If the branch were ever
reached, a caller would silently query an empty in-memory database instead
of the index.

## What should happen

STANDARDS §2: no error-suppressing idiom (`.unwrap()`, `.expect()`,
`panic!()` or an equivalent) in a production path. The fix is a type shape
where a held `IndexConn` always has its connection. The "taken after drop"
state must not exist to be handled. A closure-scoped borrow (`with_index(|conn|
…)`) or a wrapper that owns a non-`Option` connection both satisfy this, and
there are other ways. The executor picks.

## Root cause

`IndexConn` stores `Option<rusqlite::Connection>` only so `Drop` can move
the connection back into the slot. The `Option` then forces every `Deref`
to handle a `None` that can only occur after `Drop`, and the run handled it
with leaks and a panic rather than removing the `Option` from the
borrowed type.
