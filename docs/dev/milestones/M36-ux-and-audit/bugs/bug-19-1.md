# Bug 1 on phase-19: the ghost foreground gate no longer fails closed on an unreadable config

**Severity:** major
**Status:** open
**Filed:** 2026-11-08

## What's wrong

`ghost_foreground_refusal` (`src/daemon/executor/dispatch_foreground.rs`)
now takes `&Config` from `config::current()`, and its "config could not be
read" arm is gone, along with its three tests:
`ghost_foreground_refusal_refuses_a_ghost_when_the_config_is_unreadable`,
`ghost_foreground_refusal_names_the_error_under_its_context` and
`ghost_foreground_refusal_allows_a_non_ghost_when_the_config_is_unreadable`.
The doc comment above the function still says the gate fails closed.

`run_daemon` (`src/daemon/startup.rs`) still falls back to
`Config::default()` when the startup `Config::load()` fails, and installs
**that** in the handle. So a daemon started with a broken `config.toml`
runs every ghost foreground command unsandboxed on the host, because the
default has `sandbox.enabled = false`. Before this phase each call re-read
the file, got the error, and refused, which was the M32 phase-01 fail-closed
gate.

The deletion is not named in Findings.

## What should happen

While the daemon runs on fallback defaults because its startup load
failed, a ghost foreground call is refused, and the refusal names the load
error with its context chain, as before. A non-ghost call is not refused
for this reason. A later successful reload clears the condition only for
the sections it actually swaps; `sandbox` is restart-only, so the gate
stays closed until a restart with a readable file.

## Root cause

The handle cannot tell "the running config is the file's" from "the
running config is defaults because the file failed". The per-request
`Result` carried that distinction; the handle dropped it.

## Definition of done

- [ ] `ghost_foreground_is_refused_while_the_daemon_runs_on_fallback_defaults`
      exists and passes, and the refusal text names the load error.
      **Today the test does not exist.**
- [ ] The non-ghost case is covered by a test that passes.
- [ ] The doc comment above `ghost_foreground_refusal` is true.
