# Bug 1 on phase-13: `command_has_sudo` skips quoted text, so `sh -c '…; sudo …'` is no longer sudo

**Severity:** blocker
**Status:** open
**Filed:** 2026-11-07

## What's wrong

The new `command_has_sudo` (`src/daemon/utils/sudo.rs`) treats a `'…'` or
`"…"` region as argument text and skips it whole. Any `sudo` inside the
quotes is never seen.

The reviewer compared the new detector against the old regex
`(?:^|[;&|])\s*sudo\b`:

| command | old | new |
|---|---|---|
| `sh -c 'id; sudo rm -rf /x'` | true | **false** |
| `bash -c "sudo rm -rf /x"` | false | false |

The first row is a **regression**: the old regex caught it, and the new
detector does not. The second is a miss that the new design should close.

Here is the consequence. `GhostPolicy::is_safe` returns `true` for any
command that `command_has_sudo` calls sudo-free. A ghost can therefore run
`sh -c 'id; sudo rm -rf /x'` auto-approved, which the policy refused before
this phase. This is a security phase that widened what a ghost may run.

## What should happen

PE decision (2026-11-01): sudo is detected in every command position. The
string handed to `sh -c` / `bash -c` is a command, so quoted text must be
scanned, not skipped. Both commands above must count as sudo.

Detecting more is acceptable when it fails closed. So, for example,
`grep 'sudo' /var/log/auth.log` may now count as sudo. These must still
**not** match:

- `grep sudo /var/log/auth.log`
- `echo pseudo`
- `cat /etc/sudoers`
- `visudo -c`

## Root cause

The `'\'' | '"'` arm of `command_has_sudo` skips to the closing quote and
sets `at_command = false`. Nothing inside a quote is ever tested.
