# Bug 1 on phase-03: an `A` on a script or agent delete grants a *write* approval and claims a delete one

**Severity:** major
**Status:** fixed (65b6d1e9, approved 2026-11-02)
**Filed:** 2026-11-02

## What's wrong

The new `prompt_delete_ratatui` (`src/cli/commands/stream_prompts.rs:499`)
offers `[A]pprove for session` on script and agent deletes
(`build_approval_prompt("session", false)`, line 519). On `A` it calls
`record_delete_for_session` (lines 553–563), which inserts the script name
into `approval.scripts` — or the agent name into `approval.agents` — and
prints `✓ approved — script deletes are auto-approved for this session`
(line 527). Those two sets are the **write** grants:
`SessionApproval::prompt_auto_approves` (`src/cli/commands/approval.rs`)
answers `ScriptDelete` / `AgentDelete` from `self.deletes` alone, and
`ScriptWrite(name)` / `AgentWrite(name)` from exactly those sets.

Observed, from the session state after one `A` on `delete_script check.sh`
(run against the current tree, then reverted):

```
an A on a script delete must not auto-approve writes to check.sh (it does: scripts={"check.sh"})
the reply says script deletes are auto-approved; the predicate says deletes=false
```

So the answer does the opposite of what its confirmation line says: the next
`delete_script check.sh` prompts again, while the next `write_script
check.sh` — a different category the user never approved — is answered
`✓ auto-approved (session)` without asking. The agent branch is the same
with `agents`. The doc comments on `prompt_delete_ratatui` (line 496) and
`delete_kind` (line 540) state that an agent delete "may be covered by the
agent's own session name"; the predicate does no such thing. The runbook
delete arm (`stream_ask.rs`) and the schedule prompt stay Y/N, so the three
delete prompts also answer differently.

## What should happen

Phase-03 § Behaviour: "a script, runbook or agent delete with `deletes` on
are answered `approved` without asking"; the session grant for deletes is
the `deletes` category, set by `/approvals deletes on`. Spec step 4 names
the one new `A` recording — an agent **write** records the agent's name —
and nothing else. The per-name sets are write grants; a delete answer must
never widen them. A delete prompt's confirmation line must describe a grant
`prompt_auto_approves` then honours, and the three delete prompts (script,
agent, runbook) must offer the same answers.

## Root cause

`record_delete_for_session` reuses the write sets as if they were delete
grants, and `prompt_delete_ratatui` offers an `A` the spec never defined
for deletes — nothing on `SessionApproval` records a per-name delete, so
the `A` had nowhere in-spec to land and was pointed at the wrong state.
