# Bug 2 on phase-10: required mutation-check of the new non-mutation test was never captured, and the test's own claim overclaims what it verifies

**Severity:** major
**Status:** open
**Filed:** 2026-07-30

## What's wrong

Two related gaps in the round-2 (`84f5494`) submission.

**(a) The explicitly-required mutation-check of `get_does_not_mutate_stored_map`
was not performed/captured.** The refined phase doc's bug-10-1(b) notes said,
verbatim: *"Mutation-check the new test: make `get_from` write to the file (or
re-add the `prune()` call in `get()`), confirm the non-mutation assertion
fails, revert, confirm it passes."* This was restated as part of the phase's
finish condition. The executor's `### Update — 2026-07-31 03:00 (end-to-end
verification)` entry contains only the `matches()` fingerprint RED/GREEN
capture (unchanged from round 1) plus the 12-run flake block — there is no
RED/GREEN capture for the non-mutation test itself. Reviewer independently ran
the exact required check twice:

- Made `get_from` perform an unconditional `save_all(prefs)` write-back
  (byte-identical content) → `get_does_not_mutate_stored_map` **passed**
  (`exit=0`).
- Reintroduced the original defect shape, `save_all(&prune_map(prefs,
  panes))`, as the first statement of `get_from` → the test **failed**
  (`exit=101`, diff shows the stale entry pruned from the written file);
  reverting restored all 10 `pane_prefs` tests green.

The second check is the one the phase doc's instruction literally asked for,
and it does pass — so the underlying property (a `prune()`-shaped regression
is caught) holds. But the executor never ran or captured this, which is a
process violation independent of the outcome: `STANDARDS.md` §1's
mechanical-capture box and `WORKFLOW.md` § "A pasted transcript is a claim,
not evidence" exist precisely so "it works" isn't taken on the executor's
word, and this milestone has bounced seven times specifically for missing
capture of a required check.

**(b) The test's own assertion message overclaims.** `src/pane_prefs.rs:342`:

```rust
assert_eq!(before, after, "get_from must not modify the on-disk file");
```

This only detects **content** changes, not writes. The reviewer's first
mutation check above (unconditional `save_all(prefs)`, identical bytes) proves
it: `get_from` performed an unsynchronized disk write and the test passed
anyway, because the write happened to serialize back to the same JSON. That
matters beyond style — in the concurrent scenario this feature's persistence
exists for (daemon `get()` reads at T0, a `daemoneye` CLI `save()` writes at
T1, and a hypothetical regression has `get()` write its own T0 snapshot back
at T2), the T2 write can still clobber the T1 save even though its content is
"identical to what it read at T0" — content-identity at any single instant
says nothing about a write happening between two other writes. The assertion
message claims a stronger property ("must not modify") than the check
enforces (content is unchanged).

Note: the production code today does not have this defect — `get()` /
`get_from()` do not write at all (confirmed by reading
`src/pane_prefs.rs:107-121,169-175`). This is a regression-guard weakness, not
a live defect.

## What should happen

- The required mutation-check of `get_does_not_mutate_stored_map` must actually
  be run and its RED/GREEN transcript captured in a new (or amended) Update
  Log entry, per the phase doc's explicit instruction and finish condition.
- The non-mutation test should detect an unconditional identical-content
  write-back, not just a content change. The cheapest robust fix is an
  mtime check: snapshot `std::fs::metadata(prefs_path())?.modified()` before
  calling `get_from`, snapshot again after, and assert the two are equal (in
  addition to, not instead of, the existing byte-identical content check).
  Either fix the assertion message to describe what is actually checked, or
  strengthen the check to match the message — given this milestone's purpose,
  strengthening the check is preferred.

## How to fix

1. In `src/pane_prefs.rs`'s `get_does_not_mutate_stored_map` test, add an
   mtime capture around the existing byte-identical-content check:
   ```rust
   let mtime_before = std::fs::metadata(prefs_path()).unwrap().modified().unwrap();
   let result = get_from(&prefs, "my-session", &panes);
   let mtime_after = std::fs::metadata(prefs_path()).unwrap().modified().unwrap();
   assert_eq!(mtime_before, mtime_after, "get_from must not touch the on-disk file's mtime");
   ```
   (Mind filesystem mtime resolution — if this proves flaky in CI, an
   alternative is asserting on a written sentinel, e.g. temporarily replacing
   `save_all` behind a test-only counter/spy is out of scope; the mtime check
   is the pragmatic version the phase doc's own reviewer note gestures at.)
2. Run the mutation check the phase doc actually required: with the mtime
   assertion in place, (i) add `save_all(prefs)` as the first line of
   `get_from` and confirm the test now fails, (ii) revert, confirm it passes,
   (iii) separately confirm `save_all(&prune_map(prefs, panes))` (the original
   defect shape) still fails and reverting still passes.
3. Paste all RED/GREEN transcripts (content-based ones already exist from
   round 2; add the mtime-based ones) into a new
   `### Update — <date> (end-to-end verification)` entry — not folded into the
   server-authored `(complete)` entry.
