# Bug 1 on phase-02: `audit_text`'s Legacy-finding branch is untested — mutation-deletable with zero failures

**Severity:** blocker
**Status:** open
**Filed:** 2026-07-30

## What's wrong

`src/config/path_audit.rs:318-325`, inside `audit_text`:

```rust
Some(entry) => {
    if let PathStatus::Legacy { reason } = entry.status {
        findings.push(Finding {
            literal,
            reason: FindingReason::Legacy { reason },
        });
    }
}
```

This is the exact mechanism the phase doc calls "Finding 1" — the load-bearing
design decision that makes this gate catch the milestone's motivating defect:
"existence is not the property... the audit must reject `Legacy` paths in
agent-facing text. A pure existence check is a gate that cannot catch defect 4."
(phase doc, "Finding 1", lines 76-105).

At review, I replaced the `Some(entry) => { … }` arm's body with a no-op
(`Some(_entry) => {}`) — completely disabling Legacy-finding emission — and reran
`cargo test --lib config::path_audit`. **All 8 tests still passed, 0 failures.**
Restored the file afterward; `cargo build` confirms it's back to the shipped
state.

Root cause: `var/log/events.jsonl` (the one `Legacy`-status entry in
`INVENTORY`) was *also* added to `PENDING_FIX` during task 5. `audit_text`
checks `PENDING_FIX` **before** the `INVENTORY` lookup (line 306, `continue`),
so every literal that would exercise the Legacy branch is skipped before
reaching it. The only test that names Legacy status,
`legacy_entry_is_reported`, does not call `audit_text` at all — it reads
`INVENTORY` directly and asserts the static entry's `PathStatus` and reason
string, which is data, not behavior.

This is precisely the coverage failure `WORKFLOW.md` § "Coverage claims are
inadmissible without mutation proof" describes, which the phase doc's own
Architecture references section names as required reading for task 5, and it is
precisely what the phase doc's Test Plan asked for and did not get:

> **A `Legacy` entry is reported.** Audit a synthetic string naming
> `var/log/events.jsonl` and assert a finding carrying the recorded reason —
> **not merely that the vec is non-empty.**

The implemented test does the thing the bullet explicitly warns against in
spirit (checks static data, not `audit_text`'s output) and never drives
`audit_text` over any string containing a Legacy path outside `PENDING_FIX`.

## What should happen

`audit_text`'s Legacy-detection branch must be exercised by a test that fails
if that branch is removed or broken — i.e., a synthetic string containing a
Legacy-status path that is **not** in `PENDING_FIX`, asserting the returned
`Finding`'s `reason` is `FindingReason::Legacy { .. }` with the specific
recorded reason string.

## How to fix

In `src/config/path_audit.rs`'s test module, add (or rewrite
`legacy_entry_is_reported` to be) a test that:

1. Picks a path that is `Legacy` in `INVENTORY` but is asserted to be **absent**
   from `PENDING_FIX` (add that absence as an explicit assertion, so a future
   PENDING_FIX edit can't silently re-break this test the same way) — or
   introduces a second, test-local Legacy entry that never appears in
   `PENDING_FIX`, if reusing `var/log/events.jsonl` is inconvenient because it's
   legitimately quarantined right now.
2. Calls `audit_text` on a synthetic string containing that path in backticks,
   e.g. `` "see `var/log/events.jsonl` for details" ``.
3. Asserts the returned `Vec<Finding>` has exactly one entry, and that entry's
   `reason` matches `FindingReason::Legacy { reason }` where `reason` equals the
   recorded string from `INVENTORY`.

Demonstrate the mutation proof in the Update Log: show the test failing when
the `Some(entry) => { if let PathStatus::Legacy … }` branch is stubbed to a
no-op, then show it passing after restoring the branch — the same technique
used to verify this bug.
