# Bug 1 on phase-07: Missing End-to-end verification Update Log entry (mutation-check transcript)

**Severity:** blocker
**Status:** open
**Filed:** 2026-07-30

## What's wrong

The phase doc's "End-to-end verification" section (`docs/dev/milestones/M6-verification-and-hygiene/phase-07-artifact-lifecycle-policy.md:176-188`) requires a **new, executor-authored Update Log entry titled `### Update — <date> (end-to-end verification)`**, containing a mechanically-captured transcript of the mutation check from Spec task 3: an uncovered directory added under a throwaway `HOME`, a run where the gate genuinely **fails naming that directory**, output redirected to a file with `exit=$?` / `grep-exit=$?` markers, then the removal and a passing run.

No such entry exists. `grep -n '^### Update' phase-07-artifact-lifecycle-policy.md` returns only two entries:

```
219:### Update — 2026-07-30 22:48 (started)
229:### Update — ts=1785452607242 (complete, server-authored)
```

The "(started)" entry is a prose progress note. The "(complete, server-authored)" entry is the standard gate-tail capture that the phase doc explicitly disclaims as insufficient (`phase-07-artifact-lifecycle-policy.md:182-184`: *"The server-authored `(complete)` entry's 'Command output tails' block is the standard gate capture every phase gets automatically. It does not satisfy this requirement."*). Neither is the required E2E entry, and there is no pasted mutation-check transcript anywhere in the phase doc.

`STANDARDS.md` §1 is explicit that this is a Definition-of-Done blocker, not a nice-to-have:

> Every end-to-end transcript is **captured mechanically** — redirect the command's output to a file and paste that file's contents. ... A green `cargo test` run that exercises a temp-directory-scoped fake is **not** by itself sufficient.

This is the **6th occurrence of this exact defect class on M6** (per WORKFLOW.md § "A pasted transcript is a claim, not evidence" — phase 03 bounced twice for paraphrase/splice, phase 04 asserted E2E results in prose with no transcript).

**Distinguish this from what *does* exist and is genuine:** the executor wrote `mutation_check_uncovered_directory_fails_gate` (`src/config/lifecycle.rs:386-443`), an automated test that creates `var/log/rogue-test-dir`, asserts it appears in the uncovered list, removes it, and asserts the list is empty again. That is real, hermetic coverage of the *helper function* `is_covered`/`collect_existing_dirs`. It is **not** the same claim as "the gate itself goes red" — it is an in-test assertion that a function returns the right list, not a captured run of `cargo test` failing and printing a panic message naming the directory. The acceptance criterion ("The mutation check is quoted: an uncovered directory makes the test fail, naming it") requires the latter: a quoted, mechanically-captured transcript of `cargo test` actually failing.

## What should happen

The Update Log must contain a `### Update — <date> (end-to-end verification)` entry (executor-authored, not the server-authored complete entry) with a mechanically-captured transcript proving:

1. An uncovered directory added under a throwaway `HOME`.
2. `cargo test` (or the specific `every_existing_directory_has_a_policy_entry` test) run and genuinely **failing**, with output redirected to a file and pasted verbatim, showing the panic message naming the uncovered directory, plus an `exit=$?` marker showing non-zero.
3. The directory removed.
4. The same test re-run and passing, output pasted verbatim with `exit=$?` showing zero.

## How to fix

Re-run the mutation manually (not just via the in-test `mutation_check_uncovered_directory_fails_gate`, which only proves the helper is correct): temporarily create an extra, policy-uncovered directory under a throwaway `HOME` (e.g. via a one-off script or a temporary edit to the `every_existing_directory_has_a_policy_entry` test fixture), run `cargo test --lib config::lifecycle -- --nocapture 2>&1 | tee /tmp/mutation_fail.txt; echo "exit=$?" >> /tmp/mutation_fail.txt`, confirm the failure names the directory, revert, re-run and capture the pass the same way. Paste both captured files into a new `### Update — <date> (end-to-end verification)` Update Log entry in the phase doc.

For reference, independent review verification of this exact mutation (performed 2026-07-30 during review) confirmed the gate genuinely fails and genuinely passes:

```
thread 'config::lifecycle::tests::every_existing_directory_has_a_policy_entry' panicked at src/config/lifecycle.rs:335:9:
directories exist without a lifecycle policy entry:
  var/log/reviewer-injected-uncovered-dir
test config::lifecycle::tests::every_existing_directory_has_a_policy_entry ... FAILED
test result: FAILED. 0 passed; 1 failed; ...
exit=101
```
followed by, after removing the injected directory:
```
test config::lifecycle::tests::every_existing_directory_has_a_policy_entry ... ok
test config::lifecycle::tests::every_policy_entry_corresponds_to_a_real_path ... ok
test config::lifecycle::tests::mutation_check_uncovered_directory_fails_gate ... ok
test result: ok. 3 passed; 0 failed; ...
exit=0
```

This confirms the gate mechanism itself is sound — the defect is purely the missing captured transcript in the phase doc's Update Log, not a defect in `lifecycle.rs`. The executor's job is to reproduce and paste this capture into the required Update Log entry.
