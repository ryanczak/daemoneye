# Bug 1 on phase-09: Missing standalone end-to-end verification Update Log entry

**Severity:** major
**Status:** verified
**Filed:** 2026-07-30

## What's wrong

The phase doc's Update Log
(`docs/dev/milestones/M6-verification-and-hygiene/phase-09-pane-and-archive-retention.md`)
contains only two entries after the `<!-- entries appended below this line -->`
marker:

- `### Update — 2026-07-31 00:14 (started)` — a one-line note that work is
  starting.
- `### Update — ts=1785458878093 (complete, server-authored)` — the automatic
  gate-tail block (summary, gates, "Command output tails").

There is no `### Update — <date> (end-to-end verification)` entry authored by
the executor. The phase doc's own "End-to-end verification" section is
explicit and mandatory:

> **`STANDARDS.md` §1's mechanical-capture box applies.** Redirect each
> command's output to a file and paste the file's contents into a **new
> Update Log entry you author**, titled `### Update — <date> (end-to-end
> verification)`.
>
> The server-authored `(complete)` entry's "Command output tails" block is
> the standard gate capture every phase receives automatically. **It does
> not satisfy this requirement** — it has cost six bounces on this
> milestone.

`STANDARDS.md` §1's mechanical-capture box requires the red/green mutation
transcripts (with `exit=` markers) and a tempdir listing showing the old file
gone / fresh file surviving, captured mechanically (redirected command output,
not retyped or summarized). None of that is present in the phase doc. This is
the 7th occurrence of this exact class of miss on this milestone (per the
orchestrator's established finding).

## What should happen

Per `STANDARDS.md` §1 ("Every end-to-end transcript is captured
mechanically...") and the phase doc's own "End-to-end verification" section,
a standalone Update Log entry titled `### Update — <date> (end-to-end
verification)` must exist, containing:

1. The red-phase transcript (`cargo test --lib sweep -- --nocapture` with both
   cutoffs disabled) redirected to a file, pasted verbatim, ending with an
   `exit=` line.
2. The green-phase transcript (same command after `git checkout -- src/`)
   redirected to a file, pasted verbatim, ending with an `exit=` line.
3. A directory listing from one of the sweep tempdirs showing the old file
   gone and the fresh file surviving.
4. The exact warning string `retention_warnings()` produces for
   `archive_retention_days = 0`.

This review independently reproduced the required mutation evidence (see the
review's own mutation transcripts) and confirmed the underlying claims in the
executor's summary are true — but truth of the claim does not satisfy
`STANDARDS.md` §1, which fails the box "even when every claim in it is true"
per a missing mechanical capture.

## How to fix

In `docs/dev/milestones/M6-verification-and-hygiene/phase-09-pane-and-archive-retention.md`,
append a new Update Log entry titled `### Update — <date> (end-to-end
verification)` after the existing entries, containing the four items above,
each pasted from an actual redirected command run (not retyped/paraphrased).

## Resolution — 2026-07-31 (architect takeover)

Closed during the phase-09 session takeover (see the phase doc's "(architect
takeover)" and "(end-to-end verification)" entries).

**bug-09-1** — the required end-to-end entry was authored with three captured
transcripts: the cutoff mutation going red (`exit=101`, three sweep tests
failing), the revert going green (`exit=0`), and a twelve-run
`cargo test --lib` loop producing no `FAIL` lines.

**bug-09-2** — resolved by the two-part fix, not by the fix this bug originally
proposed. Adding `test_home_guard()` to the racing test alone was tried and took
the suite from 3-of-8 failing to 8-of-8, because the guard removes the luck
masking a poisoned `HOME` rather than fixing it. The actual causes were the five
sweep tests setting `HOME` without restoring it, and the phase-07 Direction B
test reading the ambient `HOME` instead of seeding its own. Both fixed; twelve
consecutive runs clean.
