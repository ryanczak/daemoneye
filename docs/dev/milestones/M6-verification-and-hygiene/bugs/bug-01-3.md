# Bug 3 on phase-01: `Drop` runs `tmux kill-server` guarded by nothing but the env var under test

**Severity:** major
**Status:** closed 2026-07-30 — verified at review round 2
**Filed:** 2026-07-30

## What's wrong

`tests/harness/mod.rs:189-196`:

```rust
impl Drop for IsolatedEnv {
    fn drop(&mut self) {
        // Best-effort cleanup: stop the daemon, then kill the private tmux server.
        let _ = self.daemoneye(&["stop"]).output();
        let _ = self.tmux(&["kill-server"]).output();
        // TempDir's own drop removes the root.
    }
}
```

`self.tmux()` resolves its target server from the `TMUX_TMPDIR` that `apply_env`
sets. So the single most destructive command in this repo's test suite is
protected by exactly the one variable the phase exists to verify — and a harness
bug in `apply_env` converts a test-teardown into "destroy the operator's tmux
server."

**This is not theoretical. It happened during this review.** Running the task-5
mutation (which deletes precisely that line) killed a live session on the
operator's default server:

```
before: de-op-probe: 1 windows (created Thu Jul 30 08:37:47 2026)
        hookcount=57
 after: no server running on /tmp/tmux-1000/default
        hookcount=0
```

The mutation the phase doc **requires** the executor to run is therefore also the
mutation that makes the teardown destructive. The phase doc even instructed
running it with a live default server ("or the mutated harness will simply start
its own default-socket server and the failure will be less informative"), which
is an instruction to point a `kill-server` at the operator's session.

**This is a spec bug.** The phase doc specified this teardown, including the
reassurance that "`Drop` running `kill-server` is safe here precisely because
`TMUX_TMPDIR` scopes it." That reasoning is circular: it is safe only while the
thing under test is correct, and teardown safety must not depend on the property
the tests are trying to establish. The executor implemented what was specified.

## What should happen

Teardown must be safe **independently** of whether `apply_env` is correct — it
should fail closed, not destructively, when isolation is broken.

The mechanism is available and costs nothing: tmux accepts an explicit socket
path with `-S`. The harness knows exactly where its private socket lives
(`$root/tmux-$UID/default`), so teardown can name it directly rather than
inheriting a resolution that may have been mutated. A `kill-server` against a
socket path that does not exist is a no-op, which is the correct failure mode.

## How to fix

In `tests/harness/mod.rs`:

1. Add a private helper returning the private server's socket path:
   `<root>/tmux-<uid>/default`. Get the uid from `libc::getuid()` (`libc` is
   already a dependency) or from the `tmux-*` directory tmux creates under the
   root — either is fine, but do not hardcode `1000`.
2. In `Drop`, replace `self.tmux(&["kill-server"])` with a command built directly
   as `tmux -S <that path> kill-server`, not routed through `apply_env`. Guard it
   on the socket path existing, so a run where the private server was never
   started is a silent no-op.
3. Leave the `daemoneye stop` call as-is — it is `HOME`-scoped and harmless.
4. Add a comment stating why teardown deliberately does not use the `tmux()`
   builder: so that a future edit does not "simplify" it back.

Note this makes the bug-01-2 mutation safe to re-run: with teardown pinned to an
explicit socket path, deleting `TMUX_TMPDIR` from `apply_env` will contaminate
the default server (which is what the test must detect) without destroying it.
Re-run that mutation only after this fix is in place.
