# Bug 2 on phase-09: `cargo test --lib` is intermittently flaky after this phase's new tests (~30% failure rate)

**Severity:** major
**Status:** open
**Filed:** 2026-07-30

## What's wrong

`cargo test --lib` does not reliably pass on the commit under review
(`0a9947bf5ebf69e3201c391698d706b12871dd13`). Running it repeatedly fails
intermittently:

```
$ for i in $(seq 1 10); do cargo test --lib 2>&1 | grep -E "^test result:"; done
test result: ok. 979 passed; 0 failed; ...
test result: ok. 979 passed; 0 failed; ...
test result: ok. 979 passed; 0 failed; ...
test result: ok. 979 passed; 0 failed; ...
test result: FAILED. 978 passed; 1 failed; ...
test result: ok. 979 passed; 0 failed; ...
test result: ok. 979 passed; 0 failed; ...
test result: FAILED. 978 passed; 1 failed; ...
test result: FAILED. 978 passed; 1 failed; ...
test result: ok. 979 passed; 0 failed; ...
```

3 of 10 runs failed. The failure is always the same test:

```
thread 'config::lifecycle::tests::every_policy_entry_corresponds_to_a_real_path' panicked at src/config/lifecycle.rs:360:17:
policy entry 'agents/*/mailbox' references a non-existent base directory 'agents'
```

I verified this is a regression introduced by this phase, not pre-existing
flakiness: checking out the parent commit (`5bd4998`, phase-08's tip, 972 lib
tests) and running the identical loop 10/10 times passed cleanly every time.
After this phase's diff (979 lib tests, +7), the same loop fails ~30% of the
time.

**Root cause:** `every_policy_entry_corresponds_to_a_real_path`
(`src/config/lifecycle.rs:344`) reads `crate::config::config_dir()`, which is
derived from the process's `HOME` environment variable, but the test does
**not** acquire `crate::test_home_guard()` before doing so. `HOME` is
process-global state (not thread-local), so when this test runs concurrently
(the default under `cargo test`, which runs tests in a thread pool) with any
test that swaps `HOME` to a scratch tempdir — including this phase's four new
tests (`sweep_pane_logs_deletes_expired_keeps_recent`,
`sweep_pane_logs_zero_is_noop`, `sweep_agent_mailboxes_deletes_expired_keeps_recent`,
`sweep_agent_mailboxes_zero_is_noop`, each of which correctly takes
`test_home_guard()` and sets `HOME` to an empty tempdir with no `agents/`
directory) — `every_policy_entry_corresponds_to_a_real_path` can observe the
foreign `HOME` mid-swap and compute `config_dir()` against a directory that
has no `agents/` subdirectory at all, failing its `full.exists() ||
entry.lazy` assertion for the `agents/*/mailbox` policy entry (which is not
marked `lazy`, per this phase's diff:
`lazy: false` replacing the prior `lazy: true`).

This phase added four more `test_home_guard()`-holding, `HOME`-swapping tests
to the suite, which mechanically increases the probability that
`every_policy_entry_corresponds_to_a_real_path` — which was already exposed
to this race before this phase, but apparently rarely enough to not have
surfaced it in the 972-test baseline (10/10 clean in this review's testing)
— loses the race and fails.

This is exactly the class of test-isolation bug the project's own convention
(`test_home_guard()`) exists to prevent, and CLAUDE.md's memory file already
flags: "Tests that mutate HOME/env must take `crate::test_home_guard()`...
not the raw `TEST_HOME_LOCK`... the accessor recovers from poisoning." The gap
here is that a test that *reads* `HOME`-derived global state without itself
mutating `HOME` is just as exposed to the race as a mutator would be, and this
one does not hold the guard at all.

`STANDARDS.md` §4 requires `cargo test` to pass before a phase is done; a
~30% intermittent failure rate on the lib suite means that requirement is not
reliably met, and this will intermittently break CI on unrelated future
phases whenever their tests happen to interleave unluckily with this one.

## What should happen

`every_policy_entry_corresponds_to_a_real_path` (or any test reading
`HOME`-derived paths without itself setting `HOME`) must not race against
tests that swap `HOME` under `test_home_guard()`. The test must acquire
`crate::test_home_guard()` for the duration of its `config_dir()`-dependent
work, exactly like every other test in this codebase that touches
`HOME`-derived state.

## How to fix

In `src/config/lifecycle.rs`, in
`every_policy_entry_corresponds_to_a_real_path` (around line 344), add
`let _lock = crate::test_home_guard();` as the first line of the test body,
before calling `crate::config::config_dir()`. This serializes it against the
four new (and any other) `HOME`-swapping tests in the suite, matching the
pattern already used by `mutation_check_uncovered_directory_fails_gate` in the
same file.
