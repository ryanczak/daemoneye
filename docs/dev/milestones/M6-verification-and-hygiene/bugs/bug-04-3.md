# Bug 3 on phase-04: unauthorized `pub use path_audit::*;` reverses a documented phase-02 decision

**Severity:** minor
**Status:** open
**Filed:** 2026-07-30

## What's wrong

`src/config/mod.rs:11` (diff in commit `67e8d6a`):

```rust
pub use load::*;
pub use path_audit::*;
pub use seeds::*;
pub use types::*;
```

`src/config/mod.rs:6` already declares `pub mod path_audit;`, so
`src/cli/commands/audit_prompts.rs` could reach everything it needs via
`use crate::config::path_audit::{PathClassification, classify_text, ...}`
without any glob re-export — and in fact that is exactly what it does today
(`audit_prompts.rs:5`: `use crate::config::{PathClassification, classify_text,
config_dir, prompts_dir};`, which resolves through the new glob, but would
resolve identically through a `path_audit::` qualified path).

Phase 02's bounce-1 fix (bug-02-2, `docs/dev/milestones/M6-verification-and-hygiene/bugs/bug-02-2.md`)
explicitly considered and rejected this exact re-export:

> Delete `#![allow(dead_code)]` ... and change `src/config/mod.rs:6` from
> `mod path_audit;` to `pub mod path_audit;`. Do **not** add `pub use
> path_audit::*;` — the sibling glob re-exports would collide.

and phase-02's own review verdict recorded it as a deliberate, verified
outcome (`phase-02-prompt-path-audit-test.md:903-907`):

> `src/config/mod.rs` still uses targeted `pub use load::*; pub use
> seeds::*; pub use types::*;` — no `pub use path_audit::*;` was added
> (correctly avoided per the bounce-1 authorization note), so there is no
> glob-collision risk.

Phase 04's Authorizations section (`phase-04-audit-prompts-command.md:176-184`)
lists exactly three things the executor may do — add `audit_prompts.rs` and
export it, add one `Commands` variant, and add `classify_text` (and private
helpers) to `path_audit.rs`. It does not authorize any change to
`src/config/mod.rs`. STANDARDS.md § 5 requires explicit phase-doc
authorization for any file not named there.

Checked whether the collision the phase-02 decision anticipated actually
occurs today: it does not. `grep`ing every `pub fn` / `pub struct` / `pub
enum` / `pub static` in `load.rs`, `seeds.rs`, and `types.rs` against
`path_audit.rs`'s public surface (`PathStatus`, `InventoryEntry`,
`INVENTORY`, `PENDING_FIX`, `FindingReason`, `Finding`,
`extract_path_literals`, `PathClassification`, `classify_text`,
`audit_text_with`, `audit_text`, `audit_asset`) finds no name overlap. So
this specific glob addition is harmless *today* — but it is (a) an
unauthorized change to a file outside the phase's Authorizations, and (b) a
silent reversal of a decision the milestone already made once, deliberately,
and recorded as correct in a prior review verdict. Silently re-opening a
settled decision without new justification is the failure mode the
Authorizations section exists to prevent, independent of whether this
particular instance happens to be safe.

## What should happen

`src/config/mod.rs` should be left exactly as phase 02 left it:

```rust
pub use load::*;
pub use seeds::*;
pub use types::*;
```

`audit_prompts.rs` should import `path_audit` items via the qualified path
(`use crate::config::path_audit::{classify_text, PathClassification};`),
which already works today since `path_audit` is `pub mod`.

## How to fix

1. Revert `src/config/mod.rs:11` — remove `pub use path_audit::*;`.
2. Change the import in `src/cli/commands/audit_prompts.rs:5` from
   `use crate::config::{PathClassification, classify_text, config_dir,
   prompts_dir};` to import `config_dir` / `prompts_dir` from
   `crate::config` and `PathClassification` / `classify_text` from
   `crate::config::path_audit` explicitly (two `use` lines, or one combined
   with an explicit `path_audit::` qualifier), so the module compiles
   without the glob.
3. Confirm `cargo build` and `cargo clippy --all-targets --all-features -- -D
   warnings` are still clean after the revert.
