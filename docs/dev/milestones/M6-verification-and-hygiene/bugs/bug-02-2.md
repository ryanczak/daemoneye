# Bug 2 on phase-02: unauthorized `#![allow(dead_code)]` in production code

**Severity:** minor
**Status:** open
**Filed:** 2026-07-30

## What's wrong

`src/config/path_audit.rs:10`:

```rust
#![allow(dead_code)]
```

This is a module-level lint-silencing attribute with no precedent anywhere
else in the codebase (`grep -rn "allow(dead_code)" src/` matches only this
line) and no authorization in the phase doc's Authorizations section, which
lists exactly two things the executor may do: add the module, and widen the
seeds.rs consts' visibility. `STANDARDS.md` § 1 DoD is unconditional: "No
`#[allow(...)]`... to mask diagnostics."

Verified it is load-bearing, not vestigial: removing the attribute and running
`cargo clippy --all-targets --all-features -- -D warnings` produces 11 `never
used` errors in the plain `lib` build (`FindingReason`, `Finding`,
`PATH_PREFIXES`, `extract_path_literals`, `normalise`, `audit_text`,
`audit_asset`, the `source` field, etc.) plus 2 more in the `lib test` build.
The module's public surface is, today, called only from its own
`#[cfg(test)]` block — nothing in `src/` outside `path_audit.rs` references it
yet, because the consumer (phase 04's `daemoneye audit-prompts`) doesn't exist
yet.

## What should happen

The phase doc's own scope makes this tension real: task 1 requires shipping
"production code, not `#[cfg(test)]`" ahead of its only consumer (phase 04).
That is a legitimate design question — whether to accept the dead-code
warning now, structure the module differently, or get explicit authorization
for the allow — and per `STANDARDS.md` § 7 ("Always-blockers, never
improvise... Spec is ambiguous between two valid implementations") it should
have been raised as a blocker in the Update Log for the phase's author to
resolve, not silently added.

## How to fix

One of:

1. Add explicit authorization for `#![allow(dead_code)]` (or a narrower,
   per-item `#[allow(dead_code)]` with a comment naming phase 04 as the future
   caller) to the phase doc's Authorizations section, with a rationale — then
   it's a documented, deliberate choice rather than a silent one.
2. Or find a structural alternative that avoids the blanket allow (e.g., a
   narrower `#[cfg_attr(not(test), allow(dead_code))]` scoped only to the
   items genuinely awaiting phase 04, with a comment naming the reason and the
   follow-up phase) — still requires the phase doc's authorization per
   `STANDARDS.md` § 5.

Either way, the allow (in whatever form it ends up) must carry a comment
naming *why* (awaiting phase 04's consumer) so it reads as a deliberate,
time-bound decision rather than a general dead-code suppression, and the
phase doc must record the authorization explicitly rather than leaving it
implicit.
