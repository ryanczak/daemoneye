# Bug 1 on phase-10: `get()` mutates on every call, unsynchronized, and the test meant to catch this is vacuous in the review environment

**Severity:** major
**Status:** verified — fixed in `84f5494`, confirmed in review round 2, 2026-07-30. `prune()` no longer runs inside `get()` (deleted); pruning moved to `save()`; `get()`/`get_from()` are pure reads. The non-mutation test is no longer vacuous — reviewer reproduced both mutation-check outcomes (see bug-10-2 for the residual weakness in that test's coverage, filed separately).
**Filed:** 2026-07-30

## What's wrong

Spec task 3 says: *"`get()` must not mutate. Make it a read. Whatever pruning
happens (task 4) must be deliberate and explicit, not a side effect of a
lookup."* The implementation puts `prune()` as the literal first statement of
`get()`:

```rust
// src/pane_prefs.rs:97-99
pub fn get(session_name: &str) -> Option<String> {
    // Prune stale entries on every read so they do not accumulate.
    prune();
    ...
```

and `prune()` unconditionally calls `save_all()`, which is a plain
`fs::write` with no atomic rename and no lock (`src/pane_prefs.rs:43-48`):

```rust
fn save_all(prefs: &HashMap<String, PanePreference>) {
    let path = prefs_path();
    if let Ok(json) = serde_json::to_string(prefs) {
        let _ = std::fs::write(&path, json);
    }
}
```

So every single call to `get()` — the read path, called from
`resolve_target_pane` on every foreground-command resolution — rewrites
`pane_prefs.json` on disk. Naming the call `prune()` and documenting it does
not change what it does: a lookup that always triggers a disk write is
exactly "a side effect of a lookup," which is the thing task 3 forbids.
Task 4 names three legitimate pruning triggers — "on load, on save, or on an
explicit call" — and "inside the read accessor" is not one of them.

**Practical consequence (not just a style violation):** `save_all()` has no
locking and no atomic write. The daemon and a `daemoneye` CLI invocation can
both call into this module concurrently. Sequence:

1. Process A (daemon) calls `get()` → reads the file (N entries) → begins
   pruning.
2. Process B (CLI) calls `save()` for a *new* session → read-modify-write
   completes first, file now has N+1 entries.
3. Process A's `prune()` finishes its own read-modify-write with its stale
   N-entry snapshot and calls `save_all()`, overwriting B's freshly-saved
   N+1-entry file back down to N (or fewer, if A's snapshot also lacks
   something else B relied on).

The freshly-saved preference from step 2 is silently lost — not because of
any fingerprint logic, but because `get()`, a function whose contract says
"read," performs an unsynchronized write on the file backing the *other*
half of this feature's persistence guarantee.

**The test that should catch write-on-read is vacuous in this environment.**
`get_does_not_mutate_stored_map` (`src/pane_prefs.rs:267-290`) calls `get()`
and asserts the file still has both entries — but in an environment with no
running tmux server (confirmed: this sandbox, and CI), `list_panes_detailed()`
returns `Err`, so both `prune()` (line 127: `Err(_) => return`) and `get()`
itself (line 105: `.ok()?`) short-circuit *before* reaching any write. The
test verified as much: instrumenting it with
`eprintln!("{:?}", crate::tmux::list_panes_detailed())` printed
`Err(Failed to list all panes)`, and the test still passes. On a machine
**with** a live tmux server — which is the machine this feature exists for —
`get()` reaches `prune()`'s `save_all()` call every time, and this test does
not exercise that path at all. It proves the short-circuit, not
non-mutation. This is exactly the failure shape this milestone exists to
eliminate: a green test standing in for an unverified property.

## What should happen

`get()` must not write to disk under any code path, on any machine
configuration. Pruning must be triggered by `save()` (which already performs
a write and already has fresh `list_panes_detailed()` data in hand) or by an
explicit, separately-named function called from a legitimate mutation point
(e.g., daemon startup, or a periodic housekeeping tick) — not from the read
accessor.

The non-mutation property must be verified by a test that is not vacuous
regardless of tmux availability. Per `STANDARDS.md` §3.3 ("inject
subprocess / external-IO dependencies behind a trait seam"), the tmux lookup
inside `get()`/`prune()` should be reachable through the same kind of pure
seam the phase already used for `matches()`, so a test can inject live pane
data without depending on an actual tmux server, and can then assert on
`save_all()`/file-mtime *not* being touched by `get()` specifically.

## How to fix

1. In `src/pane_prefs.rs`, delete the `prune();` call from the top of
   `get()` (lines 97-99). `get()` should only `load_all()`, look up the
   session, look up the live pane, and compare — no write.
2. Move the prune trigger into `save()` (call `prune()` after `save_all()`
   inserts the new entry, or fold pruning into `save()`'s existing
   read-modify-write so there is one write, not two) **or** expose `prune()`
   as `pub(crate)` and call it once from a legitimate mutation point (daemon
   startup is the natural fit, since that is also when a stale on-disk
   format from a previous version would first be seen). Whichever is chosen,
   name it explicitly in the doc comment per task 4's own phrasing ("on
   load, on save, or on an explicit call") — pick one of the three, not a
   fourth option.
3. Rewrite `get_does_not_mutate_stored_map` so it does not depend on tmux
   being absent to pass. At minimum, assert on something that fails loudly
   when `get()` writes regardless of environment (e.g., record the file's
   mtime/inode before and after, or replace the direct `list_panes_detailed()`
   call inside `get()` with an injectable seam and drive the test with a
   fake that returns live pane data matching the fingerprint — the same
   shape phase-08/phase-09 used for their trait seams).
4. Since `save_all()` remains a plain `fs::write` even after the fix, note
   in a comment (or use `tempfile` + `rename`) that concurrent processes can
   still race on `save()` vs. an explicit prune call; a full fix (atomic
   write via `.de_tmp` → rename, matching `edit_file`'s convention
   elsewhere in the codebase) is in scope for this bug only if it is cheap —
   otherwise file it as a follow-up, since the phase doc did not originally
   ask for file-level atomicity and this bug's primary requirement is
   restoring "get() must not mutate."
