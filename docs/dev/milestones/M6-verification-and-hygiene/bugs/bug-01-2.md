# Bug 2 on phase-01: the recorded mutation proof does not reproduce

**Severity:** major
**Status:** open
**Filed:** 2026-07-30

## What's wrong

The completion Update Log records:

> **Mutation proof:** Removing `TMUX_TMPDIR` from `apply_env` causes all 3 tests
> to fail — the daemon connects to the default server, modifies its hooks, and
> the `default_server_unchanged` test detects the change.

Re-run independently at review (the review skill requires it: "A claimed mutation
check is not one"). Both halves of the claim are wrong.

**Only 2 of 3 tests fail, and neither fails for the stated reason.** With a live
session on the default server and `.env("TMUX_TMPDIR", root)` deleted from
`apply_env`:

```
thread 'default_server_unchanged' panicked at tests/harness/mod.rs:143:9:
daemoneye daemon failed to start (exit exit status: 1)
stderr: daemoneye: daemon failed to start: Failed to create tmux session
        'de-test': duplicate session: de-test

test default_server_unchanged ... FAILED
test hooks_land_on_private_server ... FAILED
test daemon_boots_in_throwaway_root ... ok

test result: FAILED. 1 passed; 2 failed
```

The failure is a **session-name collision**: all three tests hardcode the session
name `de-test`, and once they share one tmux server the second and third
`start_daemon` calls collide. Both failures happen inside `start_daemon`'s
assert — `default_server_unchanged` panics before it ever reaches its snapshot
comparison. The test did not "detect the change"; it never got that far.

`daemon_boots_in_throwaway_root` passes under the mutation and always will:
`HOME` is untouched by it, so the socket and PID file are still under the
throwaway root and `ping` still succeeds. Nothing about that test observes tmux
isolation.

## What should happen

The mutation must exercise the assertion whose validity it is meant to establish,
and the Update Log must record what actually happened rather than what was
expected.

For the record, `default_server_unchanged` **is** sound — it simply was not what
the recorded mutation demonstrated. Run alone under the same mutation, with a
session live on the default server, it fails on the real comparison:

```
$ cargo test --test isolation -- --exact default_server_unchanged --nocapture
  left:  "de-op-probe2\n::exit status: 0:…client-attached\nclient-detached\n…"
  right: "de-op-probe2\nde-test\n::exit status: 0:…
          client-attached[0] run-shell -b "…/daemoneye notify client-attached #{session_name}"
          client-detached[0] run-shell -b "…/daemoneye notify client-detached #{session_name}"…"
test default_server_unchanged ... FAILED
```

That is the evidence the phase needed: the isolated daemon's own hooks appearing
on the operator's server, and a new `de-test` session alongside the operator's.

## How to fix

1. Fix the session-name collision first (bug-01-4) — without it the mutation
   cannot reach any assertion when the tests share a server.
2. Re-run the mutation with the collision fixed, and record **per-test** outcomes:
   which tests fail, and the assertion each one fails on. If a test passes under
   the mutation, say so and say why — `daemon_boots_in_throwaway_root` passing is
   expected and worth stating, not a defect.
3. Replace the "Mutation proof" paragraph in the Update Log with the actual
   quoted output of the failing run and the restored passing run.

Do not describe a mechanism you did not observe. If the observed failure mode
differs from the spec's expectation, report the observed one — that is the
finding.
