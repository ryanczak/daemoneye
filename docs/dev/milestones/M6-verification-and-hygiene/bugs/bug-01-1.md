# Bug 1 on phase-01: `hooks_land_on_private_server` asserts a string tmux always prints

**Severity:** blocker
**Status:** closed 2026-07-30 — verified at review round 2
**Filed:** 2026-07-30

## What's wrong

`tests/isolation.rs:110-118`:

```rust
let hooks_out = env
    .tmux(&["show-hooks", "-g", "pane-died"])
    .output()
    .expect("run show-hooks -g pane-died");
let hooks = String::from_utf8_lossy(&hooks_out.stdout);
assert!(
    hooks.contains("pane-died"),
    "private server does not have pane-died hook:\n{}",
    hooks
);
```

`tmux show-hooks -g <name>` echoes the hook's **name** whether or not the hook is
set. Probed at review on a bare tmux server with no daemon anywhere near it:

```
$ tmux new-session -d -s bare 'sleep 60'
$ tmux show-hooks -g pane-died          # nothing has ever set this hook
pane-died
exit=0
$ tmux set-hook -g pane-died 'run-shell "true"'
$ tmux show-hooks -g pane-died
pane-died[0] run-shell true
```

So `hooks.contains("pane-died")` is true on **any** running tmux server. The
assertion holds if the daemon never installed a hook, and it holds if the daemon
never started at all — it observes only that some tmux server answered.

This is the `WORKFLOW.md` § "Coverage claims are inadmissible without mutation
proof" failure the phase doc's own Architecture references pointed at: a spec
pinned a property that is not observable through the command it named, and the
test that "asserts" it passes on grounds unrelated to the branch.

It matters more than an ordinary weak test because of the role this one plays.
The phase doc gave it a specific job:

> This is the positive half — proving the daemon really did reach a tmux server,
> so that the negative half below is not passing vacuously (a daemon that reached
> *no* server would also leave the default one clean).

`default_server_unchanged` is only meaningful if something independently
establishes that the daemon *did* reach the private server. Nothing currently
does, so the phase's central claim rests on an assertion that cannot fail.

**This is a spec bug, not an executor fault.** The phase doc named `pane-died`
and `show-hooks -g` explicitly; the executor implemented what was specified, and
its Update Log flagged the listing behaviour it ran into. The spec text is
corrected alongside this bug.

## What should happen

The test must distinguish a server where daemoneye installed its hooks from one
where it did not — and must fail if the daemon never reached the private server.

Two facts to build on, both confirmed at review:

1. **Assert on the hook's value, not its name.** A set hook renders as
   `pane-died[0] run-shell -b '<path>/daemoneye notify activity …'`. The
   discriminating content is the index/value, and specifically the
   `daemoneye notify` command inside it.
2. **`pane-died` genuinely is installed at daemon start**, together with
   `after-new-session`, `client-attached`, `client-detached`
   (`src/daemon/mod.rs:555`–`:625`) — but the daemon **unsets all four on
   shutdown** (`src/daemon/mod.rs:942`–`:960`, `set-hook -gu`). So the assertion
   must run while the daemon is live. The current test does not call
   `stop_daemon()` before asserting, which is correct; keep it that way.

## How to fix

In `tests/isolation.rs`, in `hooks_land_on_private_server`:

- Keep querying the private server while the daemon is running.
- Replace the name-substring assertion with one that requires the hook to carry a
  daemoneye command — assert the output contains both `pane-died[` and
  `daemoneye notify`. Quote the full output in the failure message.
- Add the same value-level assertion for at least one hook that **does** appear
  in the general `show-hooks -g` listing (`client-attached` and `client-detached`
  both do — that is how the review's own mutation detected contamination of the
  default server). Two hooks checked two ways is cheap and removes the dependence
  on one command's display quirk.

Then **demonstrate the test can fail**, and record the demonstration in the
Update Log: point the harness's `tmux()` builder at a tmux server the daemon
never touched (for example, run the assertion against a bare private server you
start yourself, with no `start_daemon` call) and show the assertion failing.
Restore and show it passing. Do not adjust the assertion until it fails — if it
cannot be made to fail, say so in the Update Log and stop.
