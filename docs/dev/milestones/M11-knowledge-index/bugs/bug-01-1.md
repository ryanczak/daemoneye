# Bug 1 on phase-01: the end-to-end verification artifact was never produced, and the prose that replaced it is inaccurate

**Severity:** major
**Status:** open
**Filed:** 2026-08-03

## What's wrong

**The implementation is correct.** All four gates re-run clean at review
(`cargo fmt --all --check` exit 0; `cargo build` exit 0; `cargo clippy
--all-targets --all-features -- -D warnings` exit 0; `cargo test` exit 0 —
1044 lib + 6 bug_tracker + 4 doc_truth + 30 integration + 9 isolation).
Every acceptance criterion was independently verified at review and holds.
Both masking mechanisms are mutation-proven (see § Already verified below).
Nothing about the shipped code needs to change.

The defect is in the phase's verification record.

### Finding 1 — the required Update Log entry does not exist (major)

The phase doc's § End-to-end verification requires the two commands to be run
with output redirected to files, and the captured output pasted into an Update
Log entry **titled** `### Update — <date> (end-to-end verification)`. The spec
also states, in bold, that the server-authored `(complete)` entry does **not**
satisfy the requirement.

The Update Log contains exactly two entries: `(started)` and
`(complete, server-authored)`. There is no end-to-end verification entry, and
no captured output was pasted anywhere. The evidence was instead summarised as
prose inside the completion summary — which `docs/dev/WORKFLOW.md`
§ "End-to-end verification" names explicitly as one of the four ways an untrue
line reaches an otherwise-real transcript.

### Finding 2 — the prose claim is wrong, and wrong in a load-bearing way

The completion entry claims:

> **End-to-end verification:** All 4 new masking tests pass
> (`cargo test --lib masks` — exit 0).

Measured at review:

```
$ cargo test --lib masks
test ai::filter::tests::test_mask_json_value_masks_nested_string_values ... ok
test daemon::context::epochs::tests::test_append_epoch_masks_narrative_tally_and_artifacts ... ok
test daemon::utils::event_log::tests::test_log_event_masks_caller_fields ... ok
test daemon::context::recall::tests::recall_masks_sensitive_output ... ok
test result: ok. 4 passed; 0 failed; 0 ignored; 0 measured; 1040 filtered out
```

That command runs 4 tests, but only **3** of them are new — the fourth,
`recall_masks_sensitive_output`, is pre-existing and unrelated to this phase.
The phase actually added **6** tests. The 3 it never runs are:

- `test_mask_json_value_leaves_keys_and_non_strings`
- `test_log_event_leaves_daemon_fields_and_numbers`
- `test_append_epoch_preserves_structure`

Those three are precisely the must-NOT-change negative cases that acceptance
criterion 3 rests on (keys and non-strings untouched; structural epoch fields
byte-identical). The cited evidence does not exercise them. This is exactly
what the mechanical-capture requirement exists to prevent: the summary reads
as full coverage while the negative cases went unverified.

### Finding 3 — epochs tests deviate from the mandated home-guard idiom (minor)

The phase doc's § Test plan states that HOME-redirecting tests **MUST** use the
quoted RAII idiom, and quotes it in full. The two new tests in
`src/daemon/context/epochs.rs` instead capture and restore `HOME` inline, with
the restore as the last statements of the test body:

```rust
let _guard = crate::test_home_guard();
let tmp = tempfile::tempdir().unwrap();
let saved = std::env::var("HOME").ok();
unsafe { std::env::set_var("HOME", tmp.path()); }
... assertions ...
// Restore HOME
unsafe { match saved { Some(h) => std::env::set_var("HOME", h), None => ... } }
```

On a failed assertion the restore is unreachable and the `TempDir` is deleted
on unwind, so `HOME` is left pointing at a path that no longer exists for the
remainder of the process. That is the failure mode the RAII `Drop` idiom exists
to prevent.

**Measured blast radius today: none.** With both masking assertions induced to
fail, the full lib suite run single-threaded gives `1042 passed; 2 failed` —
the two mutated tests and no others. So this is a latent hazard and a spec
deviation, not an active defect; it is filed as minor and the fix is
mechanical.

The `src/daemon/utils/event_log.rs` tests did this correctly, using that
module's existing `with_test_home` helper.

## What should happen

1. The phase's Update Log carries an `(end-to-end verification)` entry holding
   the mechanically captured output of both commands from § End-to-end
   verification, including the `exit=` markers.
2. The evidence command covers all six new tests, so the three negative-case
   tests are actually exercised by the cited evidence.
3. Both new tests in `epochs.rs` use the RAII home-guard idiom the phase doc
   quotes, so a failing assertion cannot leave `HOME` dangling.

## How to fix

1. **`src/daemon/context/epochs.rs`** — replace the inline HOME capture/restore
   in `test_append_epoch_masks_narrative_tally_and_artifacts` and
   `test_append_epoch_preserves_structure` with the RAII guard struct quoted in
   the phase doc's § Test plan (a `TestHome` with a `Drop` impl that restores
   `HOME`). Do not change any assertion — the assertions are correct and
   mutation-proven.

2. **Run the verification block and capture it mechanically.** Use this
   corrected first command so the evidence covers all six new tests (the
   original `--lib masks` filter silently misses three of them and picks up one
   pre-existing test):

   ```sh
   cargo test --lib -- test_mask_json_value test_log_event_masks \
     test_log_event_leaves test_append_epoch_masks test_append_epoch_preserves \
     > /tmp/phase01-tests.txt 2>&1; echo "exit=$?" >> /tmp/phase01-tests.txt
   grep -rn "current_event_segment_path\|epochs_file" src --include=*.rs \
     | grep -v "config/load.rs\|path_audit\|read_epochs\|mod tests\|fn epochs_file" \
     > /tmp/phase01-writers.txt 2>&1; echo "exit=$?" >> /tmp/phase01-writers.txt
   ```

   The first file must show 6 tests run and passing. The second must list write
   uses only inside `event_log.rs` and `epochs.rs`.

3. **Append the entry** to the phase doc's Update Log, titled
   `### Update — <date> (end-to-end verification)`, pasting the contents of
   both files verbatim. Do not retype, summarise, or reconstruct them, and do
   not treat the server-authored `(complete)` entry as satisfying this.

## Already verified at review — do not redo

These held independently and need no rework:

- **`log_event` masking is real.** Deleting `crate::ai::mask_json_value(&mut fields);`
  makes `test_log_event_masks_caller_fields` FAIL.
- **`append_epoch` masking is real.** Reverting `serde_json::to_string(&masked)`
  to `serde_json::to_string(rec)` makes
  `test_append_epoch_masks_narrative_tally_and_artifacts` FAIL.
- **Choke points hold.** The writer grep returns write uses only in
  `event_log.rs:15` and `epochs.rs:115` (`epochs.rs:91` is inside `read_epochs`).
- **Spec conformance of the implementation**: values-only JSON masking with keys
  and non-strings untouched; struct clone rather than a `serde_json::Value`
  round-trip, preserving key order; daemon-generated `ts`/`event`/`pid` not
  routed through masking. All three match the spec exactly.
