# Bug 1 on phase-04: `find_in_panes` never sorts collected rows by pane id

**Severity:** major
**Status:** verified — fixed in round 2 (commit `429c001`), confirmed at round-3 review 2026-08-08
**Filed:** 2026-08-08

## What's wrong

The phase doc's Spec, Task 2 step 3, requires:

> Sort the collected rows by pane id so output is deterministic.

for the home pass, and step 4 requires the foreign pass's collected panes to
be "sorted by pane id" before taking the first `FIND_FOREIGN_MAX_PANES`.
Neither happens. `src/daemon/executor/knowledge/pane.rs`'s `find_in_panes`
collects both `home_rows` and `foreign_rows` directly from
`panes.iter()` (a `HashMap<String, PaneState>`, `src/tmux/cache.rs:134`) with
no `sort_by_key` call anywhere in the function body:

```
$ awk '/^pub async fn find_in_panes/,/^\/\/ -+$/' src/daemon/executor/knowledge/pane.rs | grep -c sort
0
```

Compare `list_panes`, four lines below `find_in_panes` in the same file, which
does the equivalent collect-then-sort correctly:

```rust
let mut rows: Vec<_> = panes
    .iter()
    .filter(|(_, state)| state.session_name == session)
    .filter(|(id, _)| chat_pane != Some(id.as_str()))
    .collect();
rows.sort_by_key(|(id, _)| id.as_str());
```

`find_in_panes`'s `home_rows` and `foreign_rows` are collected with no
equivalent `.sort_by_key(...)` call before being iterated (home pass,
`src/daemon/executor/knowledge/pane.rs` around the `home_rows` collection) or
before `.take(FIND_FOREIGN_MAX_PANES)` (foreign pass, around the
`foreign_rows` collection).

Rust's `std::collections::HashMap` uses a per-instance randomized hasher
(`RandomState`), so iteration order is not pane-id order and is not stable
across daemon restarts (a fresh `SessionCache` gets a fresh random seed). Two
concrete consequences:

1. **Non-deterministic tool output.** The same set of matching panes can be
   reported in a different order on different daemon runs, which the spec's
   own rationale ("so output is deterministic") calls out as the reason to
   sort in the first place.
2. **Non-deterministic truncation on the foreign pass.** When more than
   `FIND_FOREIGN_MAX_PANES` (20) foreign panes exist, `.take(20)` selects an
   effectively random 20 rather than the lowest-id 20 the spec intends — which
   20 foreign panes get captured (and therefore searched) varies run to run.

No existing test catches this: `find_in_panes_finds_match_in_cached_buffer`
and the other new tests each seed at most one pane whose buffer matches the
pattern, so there is never more than one row in `results` and ordering is
unobservable.

## What should happen

Both `home_rows` and `foreign_rows` sorted by pane id before use, mirroring
`list_panes`'s `rows.sort_by_key(|(id, _)| id.as_str())` — e.g.
`home_rows.sort_by_key(|(id, ..)| id.clone());` right after the home-pass
collection block, and the equivalent for `foreign_rows` before the
`.take(FIND_FOREIGN_MAX_PANES)` call.

## How to fix

In `src/daemon/executor/knowledge/pane.rs`, inside `find_in_panes`:

1. Immediately after the home-pass block that builds `home_rows` (the block
   ending in `.collect()` assigned to `home_rows`), add
   `home_rows.sort_by_key(|(id, ..)| id.clone());` before the `for` loop that
   iterates `&home_rows`.
2. Immediately after the foreign-pass block that builds `foreign_rows` (before
   `.into_iter().take(FIND_FOREIGN_MAX_PANES)`), sort it by pane id the same
   way — e.g. sort the `Vec` in place before the `.take(...)` chain, or fold
   the sort into that chain with `.collect()` + `sort_by_key` + `.into_iter()`
   as long as the sort happens strictly before the `take`.

Do not touch any other function in this file (`read_pane`, `list_panes`,
`close_bg_window`) — this bug is scoped to `find_in_panes` only.
