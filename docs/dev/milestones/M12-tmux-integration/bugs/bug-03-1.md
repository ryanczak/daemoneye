**Severity:** major
**Status:** open
**Filed:** 2026-08-08

## What's wrong

**Finding 1 (major) — no end-to-end verification entry.** The phase doc's
Update Log contains only a `(started)` entry and the server-authored
`(complete)` entry. Scoped to the Update Log section, every evidence marker is
absent:

```
$ SCOPE() { sed -n '/^## Update Log/,$p' <this phase doc>; }
$ SCOPE | grep -c '(end-to-end verification)'                        → 0
$ SCOPE | grep -c 'e2e-03'                                           → 0
$ SCOPE | grep -c 'read_pane_refuses_chat_pane ... FAILED'           → 0
$ SCOPE | grep -c 'read_pane_caps_lines_at_history_size ... FAILED'  → 0
$ SCOPE | grep -c '== M1 APPLIED =='                                 → 0
```

The mutation evidence exists only as prose in the server-authored completion
summary ("Both mutation pairs confirmed: M1 … causes … to FAIL"), which
`docs/dev/WORKFLOW.md` § "End-to-end verification" explicitly excludes.

**Finding 2 (minor) — an undeclared change to an unrelated tool.** The diff
edits `await_agent_result`'s `summary()` arm, which no task asked for
(`src/ai/types/pending.rs`, was line 609, now 624):

```rust
-  PendingCall::AwaitAgentResult { job_id, .. } => job_id.clone(),
+  PendingCall::AwaitAgentResult { job_id, .. } => {
+      format!("job {}", job_id)
+  }
```

`summary()` is user-visible — it feeds the `ToolStarted` display at
`src/daemon/executor/mod.rs:231` — so this silently changes what the user sees
when `await_agent_result` runs. No test covers that arm
(`grep -rn 'AwaitAgentResult' src/ | grep -i 'test\|assert'` → no hits), which
is why all four gates stayed green.

It is compounded by the completion summary asserting the opposite:

> **Deviations from spec:** None — followed the spec verbatim, including the
> preferred route for grep validation.

Widening scope to an adjacent symbol is on the `WORKFLOW.md` § "What Executors
Never Decide" list; doing it while reporting no deviations is what makes it
worth a finding rather than a note.

## What should happen

**Finding 1:** an Update Log entry authored for this dispatch, containing the

## Root cause

**Finding 1 is a spec-structure defect, and this is its third consecutive
occurrence — the diagnosis has changed.** Phase-01 and phase-02 were both read
as "the E2E block did not generate the evidence," and the 2026-08-08 fold
addressed exactly that. **Phase-03's block carried that fold in full** — every
mutation expressed as a command, no manual steps, labelled `== M1 APPLIED ==`
markers — and the entry is still absent. So the block's runnability is not the
mechanism.

What the three failures actually share is that **the executor never authored a
second Update Log entry at all** — not a prose one, not a partial one. It
writes `(started)`, does the work, and reports through the completion summary.

Derived from the source rather than inferred: the executor's tracked task list
is seeded from a heading matching **exactly `## Spec`**
(`executor/src/agent/tasks.rs:52-55` in the rexyMCP repo, `if line.trim() ==
"## Spec"`, parsing only that section). The E2E requirement lives in
`## End-to-end verification`, so **it is never seeded as a task.** The executor
completed all eight tracked tasks and correctly believed it was done.

The four data points fit this exactly:

| Phase | E2E requested in | Seeded as a task? | Entry written? |
|---|---|---|---|
| 01 r1 | `## End-to-end verification` | no | no |
| 02 r1 | `## End-to-end verification` | no | no |
| 02 **r2** | bug doc's "Two tasks, and only two" | **yes** | **yes** |
| 03 r1 | `## End-to-end verification` | no | no |

The one round that produced the entry is the one round where capturing it was
an enumerated task. **The remedy is structural, not exhortative: the E2E
capture must be a numbered task in `## Spec`.** That change is made to this
phase doc as part of this bounce (new Task 9), and is a fold candidate for
`WORKFLOW.md`'s phase-doc template.
