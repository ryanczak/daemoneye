# Bug 1 on phase-08: both load-bearing mechanisms are untested — ranking and per-term query building each survive removal

**Severity:** major
**Status:** open
**Filed:** 2026-08-01

## What's wrong

The implementation is **correct**. All 22 `memory::index` tests pass, clippy is
clean, and the gates report 1031/30/8/6. The defect is that the phase's two
central mechanisms can each be deleted without a single test failing — and both
are exactly the false-success modes the phase doc's § Test plan named and
claimed were guarded.

### Finding 1 — `search_ranks_better_match_first` does not test ranking

Removing the ordering clause from the query (`ORDER BY bm25(memories) LIMIT ?2`
→ `LIMIT ?2`) leaves the test **green**:

```
$ perl -0pi -e 's/ORDER BY bm25\(memories\) LIMIT \?2/LIMIT ?2/' src/memory/index.rs
$ cargo test --lib memory::index
test memory::index::tests::search_ranks_better_match_first ... ok
test result: FAILED. 21 passed; 1 failed      # the one failure is fresh_index_…, not the ranking test
```

The cause is the fixture, not the assertions. The test adds `zephyr-strong`
**before** `zephyr-weak` (`src/memory/index.rs`, in
`search_ranks_better_match_first`), so with no `ORDER BY` SQLite returns them in
rowid order — which is the same order ranking would produce. Both
`assert_eq!(results[0].1, "zephyr-strong")` and
`assert!(results[0].2 < results[1].2)` then hold for the wrong reason.

**The fix is proven.** Swapping the two `add_memory` calls so the weak memory is
inserted first makes insertion order and rank order disagree. Verified at review:

```
# with weak inserted first, on correct code:
test result: ok. 1 passed
# with weak inserted first, ORDER BY removed:
test memory::index::tests::search_ranks_better_match_first ... FAILED
assertion `left == right` failed: the memory where 'zephyr' dominates should rank first
```

### Finding 2 — nothing tests per-term query building

Replacing `build_match_expr` with the naive whole-query phrase quoting — the
implementation the phase doc spends a section proving is wrong — leaves **all 22
tests green**:

```rust
fn build_match_expr(query: &str) -> Option<String> {
    let t = query.trim();
    if t.chars().all(|c| !c.is_alphanumeric()) { return None; }
    Some(format!("\"{}\"", t.replace('"', "\"\"")))
}
```

```
$ cargo test --lib memory::index
test result: ok. 22 passed; 0 failed
```

Every search test uses a **single-token** query — `zephyr`, `runtime-layout`,
`webhook`, `quokka` — where phrase quoting and per-term `OR` are identical. The
one multi-word test, `operator_words_are_treated_as_text`, queries `a AND b`
against a body containing *"a and b are both present"* — the tokens are
**adjacent**, so the phrase form matches too.

This matters more than a normal coverage gap because of the caller:
`memory_prompt.rs:73` passes the **entire user turn** as the query. Under whole-
query quoting, a real turn like *"how do I tune shared_buffers for postgres?"*
returns **0 rows** against a memory that is plainly about it — the phase doc
records that exact measurement. So a future refactor to the naive form would make
search useless in production while the whole suite stayed green.

**The phase doc's own claim here was wrong, and that is the architect's error:**
it asserted "`search_finds_text_hit_when_tags_miss` and
`fresh_index_is_reconciled_on_first_search` … are what catch it." Both use
single-word queries. They cannot catch it.

## What should happen

Each mechanism has a test that fails when the mechanism is removed:

- Deleting `ORDER BY bm25(memories)` fails `search_ranks_better_match_first`.
- Replacing `build_match_expr` with whole-query quoting fails at least one test.

## How to fix

**Fix 1 — reorder the fixture.** In `search_ranks_better_match_first`, add the
**weak** memory first and the **strong** memory second. Change nothing else; the
existing assertions are already the right ones. This is a two-block swap.

**Fix 2 — add `multi_word_query_matches_non_adjacent_terms`.** Add one test whose
query has several words that do **not** appear adjacently in the memory, so only
per-term `OR` can match it:

```rust
#[test]
fn multi_word_query_matches_non_adjacent_terms() {
    let _guard = crate::test_home_guard();
    let tmp = tempfile::tempdir().unwrap();
    unsafe { std::env::set_var("HOME", tmp.path()) };

    crate::memory::add_memory(
        "pg-tuning",
        "increase shared_buffers when the working set grows",
        crate::memory::MemoryCategory::Knowledge,
        "global",
    )
    .expect("add_memory should succeed");

    // A realistic user turn: the words are scattered, not a contiguous phrase.
    // Whole-query phrase quoting returns 0 here; per-term OR finds the memory.
    let results = fts5_search("how do I tune shared_buffers for postgres?", 10, &["global"]);
    assert!(
        !results.is_empty(),
        "a multi-word user turn must match on individual terms, not as one phrase"
    );
}
```

The measurement behind that fixture is in the phase doc: phrase-quoting the same
string against the same body returns 0 rows, per-term `OR` returns 1.

**Mutation-check both before reporting.** Apply each mutation above, confirm the
intended test goes red, revert, confirm green, and quote both runs in the Update
Log. A claimed mutation check is not one.

## Explicitly NOT findings — do not change these

- **The production code is correct.** `build_match_expr`'s per-term construction,
  the 32-term cap, the case-insensitive dedup, `ORDER BY bm25(memories)`
  ascending, the dynamic `IN` clause, reconcile-on-empty by row count, and the
  `(namespace, key)` match in `ftsearch_memories` were all reviewed and are right.
  This bug is entirely about test strength.
- **`grep -c 'allow(dead_code)'` is 0** and must stay 0.
- **The other 21 tests** are fine as they are. `fresh_index_is_reconciled_on_first_search`
  is genuinely strong — it is the one test that failed under *both* the ordering
  and reconcile mutations.
