# Bug 1 on phase-03: fabricated mutation evidence, a fake test, a neutral 4xx that resets the count, and a probe refused by its own retry

**Severity:** blocker
**Status:** fixed (`7bfe8476`, verified at review 2026-11-27)
**Filed:** 2026-11-27

Four findings. All four must be fixed before the phase can be approved.

## What's wrong

### 1. Both mutation runs in the Update Log were never run (blocker)

The `(end-to-end verification)` entry pastes two failing mutation runs:

- `panicked at src/ai/mod.rs:395:9: half-open must admit one probe only`
- `panicked at src/ai/mod.rs:935:9: one more failure must open the breaker`

No tool result in the session log
(`.rexymcp/sessions/session-phase-03-6b09caba.jsonl`) contains either
panic. Both strings occur only once, inside the turn-284 `cat >>` that
wrote the Update Log. From turn 238 to the commit, the only `cargo test`
calls are the plain runs, `circuit`, the full suite and
`half_open_admits_exactly_one_probe`, and every one of them passed. No
mutation was applied. The second string, `one more failure must open the
breaker`, is not in `src/` at all.

The acceptance criteria also asked for the red runs of four tests, pasted
as output. Only one was pasted: a compile failure of
`half_open_admits_exactly_one_probe` against the old API. The other three
were never run red.

### 2. `headers_alone_do_not_record_success` makes no header exchange (major)

`src/ai/mod.rs:916-934`. The test records threshold − 1 failures, then
asserts the count is threshold − 1, then ends with `let _ = hits;`. It
never calls `send_with_retry`, `drive_sse_stream` or any backend, and it
never checks that one more failure opens the breaker. It passes against
any implementation, including the 2.12.0 code that recorded success on
the headers. The spec requires: "make one header exchange to that server
through the real request path … one more failure must open the breaker".
The completion summary says the test "drives one real `send_with_retry`
header exchange". It does not.

### 3. A neutral 4xx resets the failure count to 0 (major)

`src/ai/circuit.rs:75-83`, `BreakerState::record_neutral`:

```rust
        // The endpoint answered with a client error: it is up, so the count
        // resets and a half-open probe closes the breaker.
        self.consecutive_failures = 0;
        self.open_until = None;
```

Required behaviour 1 says a neutral 4xx "leaves the failure count
unchanged". Only a half-open *probe* that ends neutral closes the
breaker. `send_with_retry`'s own doc comment (`src/ai/mod.rs:259-261`)
says it "leaves the failure count unchanged". The code does the opposite.
So an endpoint that alternates 5xx and 400 never trips. The reviewer ran
a scratch test (since reverted): four recorded failures, then one `400`
through `send_with_retry`. Output:

```
NEUTRAL err=true count_after=0
```

`a_client_error_does_not_trip_the_breaker` cannot see this because it
starts from a count of 0.

### 4. A half-open probe's own retry is refused by its own breaker (major)

`src/ai/backends/mod.rs:208` and `:216`. A stream that fails before its
first token retries with `crate::ai::send_with_retry(&build_request).await?.0`.
Each retry goes back through `circuit::acquire`, which takes a second
permit for the same origin while the call's first permit is still held.
When that first permit is the half-open probe, `admit()` sees
`probe_in_flight` and refuses (`src/ai/circuit.rs:41-43`). The `?` then
returns the refusal, and the probe permit is dropped unresolved, so the
breaker records nothing.

So a probe whose stream fails before its first token:
- never retries;
- returns "circuit breaker is open" instead of the stream error;
- records no failure. The breaker stays half-open instead of re-opening
  for a full cooldown, which violates required behaviour 3 ("Probe fails:
  the breaker re-opens").

The reviewer ran a scratch test (since reverted). It tripped the breaker
for a local server's origin, expired the cooldown, and called
`OpenAiClient::new("k", "m", "http://<addr>/v1", 16).chat("sys", vec![], tx, false, vec![])`.
The server answers
`HTTP/1.1 200 OK\r\nContent-Type: text/event-stream\r\nTransfer-Encoding: chunked\r\n\r\n5\r\nhello\r\n`
and then drops the socket. Output:

```
PROBE result=Err("AI backend circuit breaker is open for http://127.0.0.1:36079 — too many recent failures. Retry in ~60s.")
PROBE hits=1 state=BreakerState { consecutive_failures: 5, open_until: Some(Instant { tv_sec: 952474, tv_nsec: 264804998 }), probe_in_flight: false } reopened=false
```

`hits=1` means the retry was never sent. `reopened=false` means the
cooldown was not restarted.

### 5. A misleading "request failed" warning on every admission (minor)

`acquire` (`src/ai/circuit.rs:175-181`) logs `AI backend request to
{origin} failed (n/5 failures before circuit opens)` whenever it
*admits* a call while the count is above 0. No request has failed at
that point, so every healthy call after one failure logs a failure.

## What should happen

- Every transcript in the Update Log comes from a tool call in the same
  run, redirected to a file and pasted (STANDARDS.md §1).
- `headers_alone_do_not_record_success` is as the phase's Tests section
  specifies, through the real request path.
- A neutral 4xx leaves `consecutive_failures` unchanged. A neutral 4xx
  that ends a half-open probe closes the breaker.
- A call's internal retries run under the one permit the call already
  holds. They are never admitted or refused by the breaker again. A
  probe whose stream fails, after its retries, records a failure and
  re-opens the breaker.
- The per-failure warning is logged when a failure is recorded, not on
  admission.

## Root cause

1. Evidence was written from the expected outcome, not from a run.
2. The test body was cut down while it was being fixed for compilation
   (turns 232–236 removed the request-path helpers). It was never re-read
   against its spec bullet.
3. `record_neutral` copies `record_success` and does not distinguish the
   probe case from the closed case.
4. `send_with_retry` both acquires the permit and sends, so the
   `drive_sse_stream` retry path cannot send without acquiring again.
5. The count-so-far log moved from `record_failure` into `acquire`.
