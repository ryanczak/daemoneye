# Bug 2 on phase-02: the lock gate now flags a plain `//` comment

**Severity:** minor
**Status:** open
**Filed:** 2026-11-27

## What's wrong

Before this phase, the lock gate's `production_lines` dropped every line
whose trimmed text starts with `//`, so a comment was never a hit. The
phase removed that filter. Instead it added a skip in `lock_unwrap_hits`
for doc comments only (`///`, `//!`), which `src/lib.rs`'s doc comment
needed. That skip is the executor's flagged deviation 2. A plain `//`
comment that quotes a guard unwrap is now a hit.

The reviewer appended a scratch test, ran it, then restored the file with
`git checkout`. Output:

```
thread 'zz_probe_plain_comment' panicked at tests/lock_invariant.rs:332:5:
assertion `left == right` failed: comment: [(1, "fn f() {"), (2, "    // m.lock().unwrap() would panic on poison"), (3, "}")]
  left: [2]
 right: []
```

The existing test `the_gate_sees_both_forms_and_ignores_comments` did not
catch this. It strips `//` lines itself before calling
`lock_unwrap_hits`, so it never exercised the gate's own comment
handling.

## What should happen

As before the phase, no comment line is a hit: `//`, `///` and `//!`
alike. The lock gate catches calls, not text about calls.

## Root cause

The `!l.trim_start().starts_with("//")` filter went away with the old
`production_lines`. Its replacement in `lock_unwrap_hits` matches only
`///` and `//!`.
