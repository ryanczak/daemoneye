# Bug 1 on phase-02: a `#[cfg(test)]` fn inside an `impl` or `trait` is scanned as production

**Severity:** major
**Status:** fixed (2026-11-27, in `82d7978b`; see the phase's review verdict)
**Filed:** 2026-11-27

## What's wrong

The statement of work says test-only items are found at any depth: "a
module, a free fn, **an impl's fn**, or anything else that carries an
attribute". Both gates check `is_test_only` only on `syn::Item`s. An
`impl` or `trait` member is a `syn::ImplItem` / `syn::TraitItem`. Its own
attributes are never read, so a `#[cfg(test)]` or `#[test]` fn inside an
`impl` or `trait` block is scanned as production code.

The reviewer appended scratch tests that called `production_lines` +
`lock_unwrap_hits`, ran them, then restored the file with
`git checkout`. Output:

```
thread 'zz_probe_trait_fn_cfg_test' panicked at tests/lock_invariant.rs:339:5:
assertion `left == right` failed: trait fn: [(1, "trait T {"), (2, "    #[cfg(test)]"), (3, "    fn h() { let g = m.lock().unwrap(); }"), (4, "}")]
  left: [3]
 right: []
thread 'zz_probe_impl_fn_cfg_test' panicked at tests/lock_invariant.rs:325:5:
assertion `left == right` failed: impl fn: [(1, "struct S;"), (2, "impl S {"), (3, "    #[cfg(test)]"), (4, "    fn h() { let g = m.lock().unwrap(); }"), (5, "}")]
  left: [4]
 right: []
```

The tree has real cases. For example, `src/cli/commands/chat_presence.rs:265`
`holds_presence` and `src/shell/registry.rs:190` `try_lock` are
`#[cfg(test)]` fns inside an `impl`. The gates read them as production
today. None of them trips a gate yet, so the tree walks are green. The
first test helper of that shape that unwraps a lock, or names a tmux
write verb, fails the gate for no reason.

The executor's completion summary says the walk covers "impl/trait fn".
It does not.

## What should happen

In both `tests/lock_invariant.rs` and `tests/tmux_read_only.rs`, an
`impl` or `trait` member that carries a test-only attribute is test-only.
Its line span, which starts at its attribute, is excluded from the
production lines. This uses the same `is_test_only` rule, and is what
`tests/hygiene.rs`'s `visit_impl_item_fn` / `visit_trait_item_fn` already
do. A production `impl` fn is still scanned.

## Root cause

`collect_test_lines` tests `is_test_only(item_attrs(item))` only for
`syn::Item`. `nested_items` turns an `Item::Impl` / `Item::Trait` into the
`Stmt::Item`s *inside* each member fn's body. It never looks at the
member's own `attrs` (`ImplItemFn::attrs`, `TraitItemFn::attrs`).
See `tests/lock_invariant.rs` `nested_items` / `collect_test_lines`;
`tests/tmux_read_only.rs` has the same code.

A second, smaller gap: `the_gate_scans_code_below_a_cfg_test_item` and
`the_gate_skips_test_only_items_and_non_guards` call
`production_lines(…).unwrap_or_default()`. In the skip test, a parse
failure yields no lines, so the test's "no hits" passes vacuously.
