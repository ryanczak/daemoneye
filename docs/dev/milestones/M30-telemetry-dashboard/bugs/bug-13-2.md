# Bug 2 on phase-13: scrolled Activity drifts as its 50-row window slides

**Severity:** major
**Status:** open
**Filed:** 2026-10-24

## What's wrong
While not tailing, `TopModel` keeps `activity_top`, an index into the
current Activity rows. Activity is the day's last 50 events
(`MAX_ACTIVITY_ROWS` in `top.rs`), so each new event drops the oldest and
every index shifts by one. The visible rows move up on every refresh while
the user reads them. This machine logged 238 events today, and
`cache_refresh_error` arrives every 2 s, so in normal use a scrolled
Activity never holds still. `activity_tails_until_scrolled` only appends
rows and never drops any, so it passes.

## What should happen
Spec item 4: while Activity is not tailing, new rows arriving do not move
the visible rows.

## Root cause
The scroll position is an index into a list whose head moves.

## Definition of done
- [ ] `scrolled_activity_holds_its_rows_as_the_window_slides` passes: 50
      rows, scrolled up 10, then a refresh whose rows are the old rows 6 to
      50 plus 5 new ones. The drawn Activity body is the same text before
      and after. `End` or `f` then shows the new rows.
