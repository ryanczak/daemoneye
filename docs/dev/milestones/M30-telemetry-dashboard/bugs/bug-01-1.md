# Bug 1 on phase-01: `tool_outcome_detail` keeps its own copy of the success rule

**Severity:** minor
**Status:** open
**Filed:** 2026-10-20

## What's wrong

Spec task 2 says `tool_outcome_detail` **must** take its `ok` from
`ToolCallOutcome::succeeded()`. It does not. Its `Result` arm still
computes `ok` with its own `starts_with("Error:")` /
`starts_with("error:")` test, the same rule `succeeded()` now holds. There
are two copies of one rule.

## What should happen

One success rule. The `ToolFinished` feedback that `tool_outcome_detail`
feeds, and the run tally that `tally_tool_outcome` feeds, must agree by
construction. Today a change to one copy leaves the other unchanged, and
the dashboard and the scorecard would then disagree about which calls
failed. The 2.0 design names this exact hazard: "the single source of
truth … must not be a second hand-kept list".

## Root cause

The executor added `succeeded()` and `tally_tool_outcome` and left
`tool_outcome_detail` untouched (the diff to `executor/mod.rs` has no
removed lines).

## Definition of done

- [ ] Inside `fn tool_outcome_detail`, `ok` comes from `succeeded()`:
      `awk '/^fn tool_outcome_detail/,/^}/' src/daemon/executor/mod.rs | grep -c 'starts_with'`
      ⇒ `0` (it is `1` against the current tree).
- [ ] `awk '/^fn tool_outcome_detail/,/^}/' src/daemon/executor/mod.rs | grep -c 'succeeded()'`
      ⇒ at least `1` (it is `0` against the current tree).
- [ ] `UserMessage` still reports `(false, Some("redirected"))` and
      `SpawnGhostSession` still reports `(true, Some("ghost spawned"))`;
      the line-count `detail` for a `Result` is unchanged.
- [ ] `tally_tool_outcome_classifies_each_outcome` and the full suite pass.
