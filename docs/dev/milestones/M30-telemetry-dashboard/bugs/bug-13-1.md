# Bug 1 on phase-13: stored panel heights disagree with the drawn layout

**Severity:** major
**Status:** fixed (2026-10-25, 7f53ba84 + b8a032bf)
**Filed:** 2026-10-24

## What's wrong
Two ways, one root cause.

- `run_tui` (`src/cli/commands/top_tui.rs`) measures `model.heights` at
  startup and when the terminal size changes, never when content changes.
  `plan_layout` sizes Runs and Shells to their content, so a refresh that
  adds shells or runs changes the drawn panels while the stored heights
  stay old. Example: 1 shell line at launch stores a Shells inner height
  of 1. With 10 shells the panel draws 6 rows, but `End` puts
  `shells_top` at 9 while the drawn window stops at 4. After that, `↑`
  needs 5 presses before the view moves.
- `draw_at` always passes the Budget body plus 1 line to `plan_layout`.
  `measured_heights` adds 1 only when a cap is set. With no cap, which is
  this machine's config, the stored Activity height is one more than the
  drawn one when the panels stack. A scrolled Activity can then never
  show its newest row. It jumps to tailing instead.

## What should happen
Spec item 6: one press past an end moves nothing, and one press back
moves one line, at every content size and terminal size.

## Root cause
`plan_layout`'s inputs are computed twice, in `draw_at` and in
`measured_heights`, and the second copy runs only on resize.

## Definition of done
- [ ] `stored_heights_match_the_drawn_layout` passes. For each of cap 0 and
      cap 10, and for content that grows after the first measure (1 shell,
      then 10; 2 runs, then 20), the stored Runs, Shells and Activity
      heights equal the inner heights of the rects `draw_at` lays out, with
      no resize in between.
- [ ] `plan_layout` is called from one place in the non-test part of
      `top_tui.rs`, so the drawn layout and the stored heights cannot
      disagree again: the harness prints `layout_inputs=1`.
