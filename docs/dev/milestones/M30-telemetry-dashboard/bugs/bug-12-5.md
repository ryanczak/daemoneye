# Bug 5 on phase-12: the fade mapping underflows when Runs overflows

**Severity:** major
**Status:** fixed (2026-10-24, def7352a)
**Filed:** 2026-10-24

## What's wrong
The fade mapping in `draw` (`src/cli/commands/top_tui.rs`) recomputes the
Runs window with `let start = 1.max(row + 1 - rows_visible);`. When the
body has more lines than the panel and the selection is near the top,
`row + 1 < rows_visible` and the `usize` subtraction overflows. With 20 runs
(21 body lines), the panel at its 12-line cap and the selection on run 0,
the expression is `1 + 1 - 11`. A debug build panics ("attempt to subtract
with overflow"); reproduced in isolation with the same arithmetic. A
release build wraps, `kept` ends up holding only the column header, and no
run dims. This machine has 34 run logs, so `top` hits it on launch.

## What should happen
The live screen draws any number of runs at any selection without
panicking, and the visible finished runs dim.

## Root cause
`draw` repeats `runs_window`'s window arithmetic rather than using it.
`runs_window` guards the subtraction behind `row >= start + rows_visible`;
the copy dropped the guard. Two copies of the arithmetic can drift again.

- [ ] `screen_fades_with_more_runs_than_fit` passes: 80×24, 20 runs where
