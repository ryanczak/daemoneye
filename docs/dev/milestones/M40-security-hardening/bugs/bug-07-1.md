# Bug 1 on phase-07: `remove_schedule` can panic the daemon task on a removal race

**Severity:** major (a Definition of Done violation: a new `expect` in a production path)
**Status:** open
**Filed:** 2026-11-26

## What's wrong

`remove_schedule` (`src/daemon/executor/schedule.rs`, around line 370)
looks the job up twice:

```rust
if !schedule_store.list().iter().any(|j| j.id == job_id) {
    return Ok(ToolCallOutcome::Result(format!("Job {} not found", job_id)));
}
let (name, kind, action) = schedule_store
    .list()
    .iter()
    .find(|j| j.id == job_id)
    .map(|j| (j.name.clone(), j.kind.describe(), j.action.describe()))
    .expect("job was found above");
```

Each `list()` takes and releases the store's read lock. Another removal can
land between the two calls: the `daemoneye schedule delete` CLI subcommand,
another chat session's approved `delete_schedule`, or a one-shot job's
cleanup. In that case the second lookup is `None`, and the `expect` panics
inside the daemon's tool-call task.

STANDARDS § Definition of Done forbids a new `unwrap()` / `expect()` /
`panic!()` in a production path. Before this phase, the production part of
`schedule.rs` had none.

## What should happen

`remove_schedule` looks the job up once. If the job is missing, whenever
that happens, it returns today's `Job <id> not found` text, with no prompt
and no panic. A job that vanishes after the prompt is already handled by
the `Ok(false)` arm of the store call.

## Root cause

A check followed by a separate fetch, with no lock held across the two,
plus an `expect` that assumes nothing changed in between.
