# Bug 1 on phase-12: `passwd_name` retries on every failure, not only on `ERANGE`

**Severity:** minor. The result is still correct, but the spec contract is
violated, and on a slow name service (LDAP, sssd) one approval label can cost
around 11 lookups.
**Status:** closed (2026-11-26, fixed in `f0a99394`; the 8-byte start in the DoD was unsatisfiable on glibc, see the phase's review verdict)
**Filed:** 2026-11-26

## What's wrong

`passwd_name_from` (`src/daemon/executor/shell_label.rs`) doubles the buffer
and calls `getpwuid_r` again whenever `passwd_name_with_buffer` returns
`None`. That `None` covers every failure, not just `ERANGE`:

- the uid has no passwd entry;
- the name service returned an error (`EIO`, `ENOENT`, …);
- the name is empty;
- the name is not UTF-8.

Each of these loops until the buffer reaches the 1 MiB cap. That is about 11
`getpwuid_r` calls from glibc's 1024-byte `sysconf` start, and 18 from the
test's 8 bytes. Only then does it give the same `None`.

The added `if rc == libc::ERANGE { return None; }` returns exactly what the
next line returns, so it distinguishes nothing.

`local_username` builds the label for every foreground approval
(`dispatch_foreground.rs`). A container uid with no entry pays the whole
ladder on every prompt.

Two smaller defects:

- the new `unsafe { libc::sysconf(...) }` has no `// SAFETY:` comment, which
  the phase's Authorizations required for every FFI call;
- `passwd_name`'s doc comment still says it returns `None` when "the buffer
  is too small".

## What should happen

The phase spec says to retry `getpwuid_r` on `ERANGE`, doubling up to a 1 MiB
cap.

- Only an `ERANGE` result leads to another attempt.
- Every other outcome ends the lookup on that attempt, as it did before the
  phase: found, no entry, an error code, an empty name, a name that is not
  UTF-8.

## Root cause

The per-attempt function collapses "buffer too small" and "no answer" into
the same `None`. The loop therefore cannot tell them apart and retries both.
