# Bug 1 on phase-04: the "without firing" half of the watcher exit test cannot fail

**Severity:** minor
**Status:** open
**Filed:** 2026-09-10

## What's wrong

`watcher_exits_without_firing_when_the_run_is_gone`
(`src/daemon/run/cancel.rs:410`) builds **two unrelated channel pairs** and
asserts on the wrong one:

```rust
415:        let (_, mut signal) = RunCancelSignal::new();
416:        let (watch_handle, _) = RunCancelSignal::new();
417:        let watcher = tokio::spawn(watch_stop_sentinel(
418:            id,
419:            watch_handle,
420:            Duration::from_millis(10),
421:        ));
```

The watcher is handed `watch_handle` from the **second** pair, whose receiver is
discarded into `_`. The asserted `signal` comes from the **first** pair, whose
sender is discarded into `_` on the same line it is created. Nothing in the
process holds a sender for `signal`, so the test's closing assertion —

```rust
        assert!(
            !signal.is_cancelled(),
            "exiting without a sentinel must not fire the signal"
        );
```

— can never fail, whatever the watcher does.

Observed, by mutation: adding `handle.cancel(CancelReason::UserStop);` immediately
before the `return` in the deregistration branch of `watch_stop_sentinel`
(`src/daemon/run/cancel.rs:212`) makes the watcher fire a spurious cancellation on
a run that is already gone — and the test still reports
`test result: ok. 1 passed; 0 failed`.

The sibling assertion in the same test, `assert!(watcher.is_finished(), ...)`, is
real: the executor's own mutation 3 reddened it, and it is what makes the test
worth keeping.

## What should happen

The phase doc's § Test plan names **both** halves of this test:

> `watcher_exits_without_firing_when_the_run_is_gone` — no sentinel; drop the
> guard; advance time well past several polls; **the signal is not cancelled**
> and the task has returned.

`watch_stop_sentinel`'s own doc comment states the same contract
(`src/daemon/run/cancel.rs:203`): "The loop returns — **without firing** — as soon
as the run is no longer registered." STANDARDS §3.1 requires a test for "the
boundary cases the function's contract names". No other test in the module covers
the no-spurious-cancellation property, so it is currently unguarded.

The observed signal must be the receiver **paired with the handle the watcher was
given**, so that a watcher which fires on a deregistered run reddens this test.

## Root cause

A single-pair construction was written as two `RunCancelSignal::new()` calls at
`src/daemon/run/cancel.rs:415-416`. `RunCancelSignal::new()` returns
`(RunCancelHandle, RunCancelSignal)` — the handle and receiver of **one**
`watch::channel`. Splitting the call in two severs the observed receiver from the
sender under test; each `_` binding drops its counterpart immediately. The
compiler cannot flag this because both halves are individually well-typed, and the
assertion is vacuously true rather than absent, so the test count and the mutation
check on the `is_finished` half both look healthy.

The correct shape is one call, as the sibling test
`watcher_fires_user_stop_and_clears_the_sentinel` (`src/daemon/run/cancel.rs:380`)
already does: `let (watch_handle, mut signal) = RunCancelSignal::new();`.
