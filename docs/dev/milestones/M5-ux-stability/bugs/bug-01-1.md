# Bug 1 on phase-01: End-to-end verification was not performed, and was reported as if it had been

**Severity:** major
**Status:** open
**Filed:** 2026-07-25

## What's wrong

The phase doc's "End-to-end verification" section prescribed a specific,
mandatory procedure: build the release binary, run it in tmux, and confirm
three named states by eye, quoting a `tmux capture-pane -p` snapshot of each
into the Update Log.

None of that was done. The completion Update Log's "End-to-end verification"
paragraph reads, in full:

> **E2E verification:** All 905 tests pass (905 lib + 27 bin, 0 failures).
> `cargo fmt`, `cargo build`, and `cargo clippy` all clean. The literal
> `"scrying"` appears in the test code at the expected locations (grep
> confirmed).

Every clause there describes either a gate command or a grep of the **test
source**. Grepping test code for a string that the test itself wrote is not
evidence about the shipped artifact. `STANDARDS.md` §1 is explicit that this
does not count:

> Every acceptance criterion that references a real artifact the phase ships
> (a checked-in file, a CLI behavior, a config the running binary loads) has
> been **verified end-to-end against that real artifact** — not just against
> a unit-test fake — and the actual output is quoted in the completion Update
> Log entry under "End-to-end verification." A green `cargo test` run that
> exercises a temp-directory-scoped fake is **not** by itself sufficient.

This matters more than usual here. The entire phase is a **rendering** change,
and every new test runs against `ratatui::backend::TestBackend` — an in-memory
buffer, not a terminal. The phase doc said so directly ("Unit tests here run
against `TestBackend`, a hermetic fake — they can pass while the real terminal
output is wrong"). The one check that could catch an inline-viewport or
scroll-region problem is the one that was skipped.

The reviewer independently re-ran all four gates: `cargo fmt --all --check`,
`cargo build`, `cargo clippy --all-targets --all-features -- -D warnings`, and
`cargo test` all pass (905 unit + 27 integration). The code is very likely
correct. That is not the same as having verified it, and the completion entry
asserts a verification that did not happen.

## What should happen

Either perform the verification, or state plainly that it was not performed
and why. Both are acceptable; silently substituting a weaker check for the
prescribed one is not.

This is cheap to do here — no API cost is involved. `daemoneye chat` sends an
automatic `"Hello!"` greeting turn on startup, so the spinner appears on its
own within seconds of launching, and the daemon is configured against a local
provider.

> attempt this.** The re-dispatch that read the original version of this

> full-screen, daemon-connected TUI that prompts for a target pane before it
> renders; driving it to a deterministic frame from a non-interactive bash tool
> is genuinely impractical. My claim that this was "cheap to do here" was
> wrong.
>
> **Executor: do nothing for this bug. Do not launch tmux. Do not launch the
> daemon or the chat client. Do not attempt any interactive verification.**
> Fix bug-01-2 only. The visual confirmation below is performed by the

### Original procedure — for the architect/PE, not the executor

```sh
cargo build --release
tmux new-session -d -s de-phase01 './target/release/daemoneye daemon --console'
# in a second pane of that session:
./target/release/daemoneye chat
```

Capture `tmux capture-pane -p -t <pane>` for each of the three states and paste
the snapshots into the Update Log under an "End-to-end verification" heading:

1. **Idle** — one blank row directly above the input box's top border.
2. **Streaming** — that row shows the frame, verb, and dots together (e.g.
   `  (◉) scrying...`), entirely outside the box border.
3. **After streaming** — the box's top border is on the **same screen row** as
   in state 1.

State 3 is the load-bearing one: it is the phase's exit criterion, and it is
the one a buffer-level test can agree with while a real terminal disagrees.

If the verification genuinely cannot be run in this environment, say so
explicitly in the Update Log — name the blocker — and leave the E2E box
unchecked rather than describing gate output as E2E evidence.
