# Bug 1 on phase-05: a scheduled ghost job that cannot start is never marked done

**Severity:** major
**Status:** open
**Filed:** 2026-11-17

## What's wrong

In `run_scheduled_job_inner` (`src/daemon/scheduled.rs`), the
`ActionOn::Ghost` arm's `Err(e)` branch of
`GhostManager::start_session_with_config` (around line 347) now publishes
the `[Ghost Shell Failed] Scheduled job '…' could not start: …` notice and
does nothing else. Before phase 05 that branch ended with:

```
store.mark_done(&job.id, false, Some(msg));
```

The phase dropped that line while it moved the call from
`inject_ghost_event` to `publish_ghost_event`. The `msg` the branch builds
is now only logged.

## What should happen

The spec (Spec task 3) changed the delivery call only: "each
`inject_ghost_event(…)` becomes `publish_ghost_event(…)` with the same
format string". Every other ghost branch in that arm still records its
outcome in the store (the Skipped branch, the runbook-load failure, and
both trigger outcomes), and this one must too. A job that cannot start
must leave `Running` with `last_error` set, so `mark_done` reschedules a
recurring job. Without it the job stays `Running` until a daemon restart's
`recover_interrupted`.

## Root cause

An over-wide edit: the deletion span for the old
`inject_ghost_event(…).await;` call took in the `store.mark_done` line
after it. Every other arm's `mark_done` survived. No test covers the
branch, because `start_session_with_config` has no reachable error path
today, so the gates stayed green.

## Definition of done

- [ ] `git diff 4df97778 -- src/daemon/scheduled.rs | grep -c '^-.*store.mark_done'`
      prints `0` (it prints `1` against the current tree): no `mark_done`
      line is removed relative to the pre-phase base.
- [ ] The restored call sits in the could-not-start `Err` branch, after
      the `publish_ghost_event` call, passing the branch's `msg`.
- [ ] `cargo test` reports **2989** lib tests passed, **not** 2990: the fix
      adds nothing.
