# Bug 3 on phase-03: the "no divergence" verification is wrong — `null` and `{}` args disagree for all-optional-args tools

**Severity:** major
**Status:** closed (fixed by architect takeover 2026-08-17, commit 4dcebf0)
**Filed:** 2026-08-17

## What's wrong

The corrected `19:13` Update Log entry closes with a new claim:

> the bug-03-2 latent divergence between the predicate's `&call["args"]`
> (`gemini.rs:33`, JSON `null` when Gemini omits `args`) and the drain loop's
> `unwrap_or_else(|| json!({}))` (`gemini.rs:348-352`) is **not** a
> divergence. For every tool whose args are not required, `dispatch_tool_event`
> accepts `json!(null)` and `json!({})` identically — verified by a throwaway
> integration test … covering `list_panes`, `list_schedules`, `list_scripts`,
> `list_runbooks`, `list_agents`, `schedule_command`, `run_terminal_command`,
> `cancel_schedule` with both arg forms: every case agreed

The architect re-ran the check with the omitted class of tool included.
**They do not agree.** Measured on the delivered tree (`e54e683`), printing
`dispatch_tool_event("id", tool, &args, None).is_some()` for each form:

```
get_terminal_context: null=false empty=true      <-- disagree
list_memories:        null=false empty=true      <-- disagree
list_panes:           null=true  empty=true
list_schedules:       null=true  empty=true
run_terminal_command: null=false empty=false
```

The eight tools the throwaway test covered are precisely the set where
agreement is guaranteed and cannot discriminate:

- `list_panes`, `list_schedules`, `list_scripts`, `list_runbooks`,
  `list_agents` return `Some(...)` unconditionally in `dispatch_tool_event`
  (`src/ai/tools/dispatch.rs:27-43`) — they never deserialize args at all, so
  both forms trivially agree at `true`.
- `run_terminal_command`, `schedule_command`, `cancel_schedule` have
  **required** fields, so `from_value` fails for both forms — they trivially
  agree at `false`.

The discriminating case is a tool that goes through `dispatch::<T>` whose
fields are **all optional**: `get_terminal_context`
(`GetTerminalContextArgs`, `src/ai/tools/args.rs:117-120`, single
`#[serde(default)] scope: Option<String>`) and `list_memories`. Serde does
not treat JSON `null` as an empty struct — `from_value::<T>(Null)` fails with
an invalid-type error while `from_value::<T>({})` succeeds on all-default
fields. Neither tool appears in the test's list.

So the divergence bug-03-2 asked about is **real and still present**:
`part_counts_as_token` (`gemini.rs:31-36`) passes `&call["args"]`, which is
`Null` when Gemini omits `args` — and the drain loop's comment at
`gemini.rs:346-347` says Gemini does exactly that ("Gemini omits `args`
entirely for calls that take no arguments"). For a frame whose only content
is a `functionCall` to `get_terminal_context` with no `args`, the predicate
returns `false` while the drain loop emits the tool call.

**No user-visible misbehavior results today**, because the three inline
`first_token_seen = true` assignments still cover the emission sites — the
flag gets set regardless. The defect is that the predicate misreports, which
is the same "two implementations that can drift" condition bug-03-1 was filed
to eliminate. It is one refactor away from mattering: whoever later removes
the now-redundant inline assignments, trusting the predicate, silently
reintroduces a stall-classification bug on no-argument tool calls.

**All four gates are green** on the architect's independent re-run (fmt,
build zero warnings, clippy exit 0, `cargo test` 1310 + 6/8/30/9, 0 failed),
and `git diff 545379e HEAD -- src/` is empty, confirming the round changed no
production code as claimed.

## What should happen

Two things, and the second matters more than the first.

**The predicate must use the same args default as the drain loop.** The
constraint: `part_counts_as_token` and the emission path must agree on every
frame — including a `functionCall` with `args` omitted. The drain loop's own
`unwrap_or_else(|| json!({}))` at `gemini.rs:348-352` is the behavior to
match. Pin it with a test case that fails against the current tree: a frame
`{"candidates":[{"content":{"parts":[{"functionCall":{"name":"get_terminal_context"}}]}}]}`
must count as a token.

**The claim in the Update Log must be corrected, and the test that produced
it must not be deleted.** The `19:13` entry currently asserts a verified
non-divergence that is false. The reason it passed the executor's own review
is that the sample was drawn from the non-discriminating cases; a deleted
test cannot be re-run by anyone checking the claim later. Whatever test
establishes the corrected answer stays in `tests/` or in the `gemini.rs` test
module as a permanent, re-runnable assertion.

## Root cause

The bug-03-2 DoD said "Determine whether `dispatch_tool_event` agrees between
the two forms for a no-argument tool call … Do not assert either way without
running it." A test *was* written and *was* run — the process was followed.
It sampled eight tools, none of which can distinguish the two forms, and the
uniform `true`/`false` agreement across that sample read as confirmation.

The mechanism is sampling without a discriminating case: a verification whose
sample cannot produce the failing outcome will always confirm. It is the same
shape as the two earlier defects on this phase, one layer up — bug-03-1's
criterion could not fail for a test-local predicate, bug-03-2's mutation could
not fail for a direct-call test, and this round's sample could not fail for
tools that never deserialize args. Each time, a check that could only return
one answer was read as evidence.

The architect's bug-03-2 DoD named the question but not the case that answers
it; the tools with all-optional args are where the two forms can differ, and
saying so would have cost one sentence.
