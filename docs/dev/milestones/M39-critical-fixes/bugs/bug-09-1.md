# Bug 1 on phase-09: the cap re-copies 16 MiB per chunk; the deadline evidence is wrong

**Severity:** major
**Status:** closed (fixed in 47548618, verified 2026-11-24)
**Filed:** 2026-11-24

## What's wrong

The architect reviewed `ded2f1c2`.

1. **Once past the cap, every chunk re-copies the whole buffer.**
   `drop_middle_of_buf` (`src/shell/client_read.rs`) cuts `buf` back to
   exactly `OUTPUT_CAP`. The next chunk is therefore over the cap again,
   so every later chunk:
   - copies the ~16 MiB tail into a new `Vec` (`buf[tail_start..].to_vec()`);
   - then writes it back.

   A PTY delivers chunks of about 4 KiB, so `yes` past the cap costs about
   32 MiB of copying per 4 KiB of output. The cap test streams 32 MiB in
   64 KiB chunks and already takes about 15 s.
2. **The note's count is wrong.** The note reports `{over}`, which is only
   the overflow of the chunk that triggered the cut. The previous note sits
   in the region being dropped, so the final note names the last chunk's
   size, not the total dropped. For the cap test it says about 64 KiB
   when about 16 MiB were dropped.
3. **The deadline half rests on false evidence.** No code was added to the
   data path. The only change there is the rename
   `handle_read_timeout` → `handle_slice_end`, and its doc comment now
   claims "Also run on the data path when a slice's window ends with data
   still arriving". That is false.

   The architect ran three probes. First,
   `continuous_output_still_times_out` and
   `continuous_output_answered_ctrl_c_returns_the_outcome` **pass on the
   pre-phase reader** (`2e1fc318`), in 6.01 s. The Update Log's "red runs"
   for them are not real runs against that tree. The pasted mutation check
   disabled the `Err(_)` **timeout** arm, which those tests do use, not a
   data-path check.

   Second, an instrumented old reader showed why. The deadline is absolute,
   so the slice's end becomes the deadline. The 100 ms gaps between chunks
   leave a read pending when it passes, and `timeout_at` fires.

   Third, `read_to_marker` was run over a `UnixStream::pair` whose writer
   keeps the socket full with `write_all` of 64-frame batches. It **still
   times out on schedule**: `timed out after 1s`, 6.18 s with the grace.
   Tokio's cooperative budget makes a ready socket read return `Pending`
   every so often, and `timeout_at` polls its timer then.

   So **the deadline half of C3 does not reproduce**. Only the unbounded
   buffer is real.
4. **Nit:** the cap test asserts `output.len() <= OUTPUT_CAP` twice, and
   `note_start < cut` holds for any note at all.

## What should happen

- **Amortized cuts.** A cut happens at most once per some fixed fraction
  of the cap in new output, for example by cutting well below the cap
  rather than exactly to it. Steady output past the cap must not copy the
  buffer on every chunk.
- **The cut logic is testable.** Put it in a small helper or type that a
  test can drive directly with a run of chunks, and that says how many
  cuts it made.
- **The note counts every dropped byte.** There is exactly one note, and
  its `N` is the **total** dropped since the begin marker. For a command
  that printed `T` bytes between its markers:
  `N + (output length − note length) == T`.
- **The output stays bounded:** no longer than the cap, with the head
  through the begin marker and the latest tail, and the exit code real.
- **The deadline half is honest.**
  - Restore the `handle_read_timeout` name and its original doc comment,
    or make the comment true. Don't add data-path code for a bug that
    doesn't reproduce.
  - Keep the two continuous-output tests, relabelled **preservation**
    tests that pin today's behaviour.
  - Correct the Update Log, and say how the deadline half was closed.

## Root cause

`drop_middle_of_buf` targets a length of exactly `OUTPUT_CAP`, so the
overflow check passes again on the next chunk. It formats the note from
the per-call overflow and keeps no running total. The deadline tests send
with 100 ms gaps, and a gap ends the read at the deadline on the old code
too.
