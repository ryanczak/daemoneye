# Bug 1 on phase-10: the pipelining test's doc comment claims a red state that cannot happen

**Severity:** minor
**Status:** open
**Filed:** 2026-11-24

## What's wrong

`host_parses_each_pipelined_frame_from_its_own_offset` (`src/shell/host.rs`)
has this doc comment:

> With the pre-S4b slice (`&line[..end]`) the second parse sees both frames
> and answers `Error { "malformed frame: …" }`.

That is false. The executor's run showed the test **passing** with the old
slice in place, and the executor flagged it correctly in its completion
notes. Its explanation was wrong, though: it said `serde_json` accepts the
concatenated frames, but `from_slice` rejects trailing characters.

## Root cause

`handle_connection` reads each request with
`reader.read_until(b'\n', &mut line)`, which stops at the **first** newline.
So `line` never holds more than one complete frame, plus at most the partial
left by a cancelled read. The frame loop therefore only ever finds one frame,
at `offset == 0`, where `&line[..end]` and `&line[offset..end]` are the same
bytes. S4b is **latent**: the slice was wrong but unreachable. The fix is
still correct and stays. The architect's phase doc claimed "red today"
without probing it, so this is a spec bug, not an executor error.

## What should happen

- The test stays, as a **preservation** test. It pins end-to-end that two
  requests written in one `write_all` each get their own correct response.
- Its doc comment says what is true:
  - it is a preservation test;
  - `read_until` delivers one frame per loop pass, so the slice was
    unreachable, and the test passes on either slice;
  - it guards the pipelining behaviour against a reader change, for example
    one that reads into the buffer in bulk.
- Nothing else changes: no production code, no other test.
