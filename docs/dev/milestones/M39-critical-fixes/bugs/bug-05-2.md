# Bug 2 on phase-05: the shell-code operand misses option clusters and absolute shell paths

**Severity:** major
**Status:** open
**Filed:** 2026-11-24

## What's wrong

The architect probed `command_has_sudo` on `bb87a6f9`:

```
false bash -lc '$S id'          false bash -x -c "$X"
false sh -ec "$X"               false sh -c -- "$X"
false /bin/sh -c "$X"           false /bin/bash -c 'sud? id'
true  sh -c "$X"                true  env bash -c "$X"
```

The bug-05-1 decision makes the fail-closed rule apply to a shell's `-c`
operand. It currently fires only for the exact spelling `<shell> -c
<operand>`. Two other common ways to write the same thing get past it:

- An option word before or around `-c`. This includes a combined flag such
  as `-lc` or `-ec`, a separate option such as `-x` before `-c`, and `--`
  after `-c`.
- A shell named by an absolute path, such as `/bin/sh` or `/bin/bash`.

`bash -lc '…'` is the usual way to run a login-shell command, so this is a
plain bypass of the fail-closed rule.

## What should happen

Each of the six commands above returns `true`. `find . -name '*.log'`,
`grep 'foo.*bar' f` and the rest of `sudo_detect_quoted_arguments_stay_clear`
stay `false`.

## Root cause

In `scan_shell_command` (`src/daemon/utils/sudo.rs`), the `code_operand`
assignment at the end of the word arm does two things wrong:

- It compares the whole word text to `"sh" | "bash" | …`, where
  `is_elevator` compares the basename.
- It keeps the flag on through exactly one following word, and only when
  that word is literally `-c`.
