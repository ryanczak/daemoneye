# Bug 1 on phase-03: other spellings of Space and Enter still hide `sudo` from the client

**Severity:** major
**Status:** closed (2026-11-23, fixed by `68ce1c3a`, architect takeover)
**Filed:** 2026-11-23

## What's wrong

1. **(major) The sudo decision text misses key spellings the key parser
   accepts.** `sudo_decision_text` (`src/daemon/executor/knowledge/shell_input.rs:71`)
   maps only the exact strings `"Space"` and `"Enter"`. The key parser is
   wider than that. `named_key` (`src/shell/keys.rs:244`) lowercases the
   name, so `space`, `SPACE`, `enter` and `ENTER` are the same keys.
   `C-m` encodes to `\r` and `C-j` to `\n` (`legacy_byte`), both of which
   end the line in a shell. The decision text drops every one of those,
   because each is longer than one character. The reviewer checked this
   with a scratch test that has since been reverted:

   ```
   lower="sudox" sudo=false | cm="echosudo x" sudo=false | bytes(space,enter)=Ok([32, 13])
   ```

   With keys `["s","u","d","o","space","x","enter"]` the shell receives
   `sudo x⏎`, but the decision text is `sudox`, so the prompt says
   `sudo: false`. With keys
   `["e","c","h","o","C-m","s","u","d","o","Space","x","C-m"]` the shell runs
   `echo` and then `sudo x`, but the decision text is `echosudo x`. Both
   calls auto-approve under `ApprovalsConfig::default()`. That is the S2b
   defect this phase exists to close.

   The phase doc caused this: its statement of work named only `Space` and
   `Enter`. The executor did what the doc said.

2. **(minor) The production approval logic lives in a method named for
   tests.** `SessionApproval::auto_approves` (`src/cli/commands/approval.rs:124`)
   now only calls `auto_approves_for_tests`. That method is not
   `#[cfg(test)]`, and it holds the real decision. Production code must not
   sit under a `_for_tests` name. Separately, `resolve_send_input_shell`
   (`dispatch_send_input.rs`) computes `r.owner.key()` into `_owner_key`
   and throws it away.

## What should happen

The client treats a `send_input` call as sudo whenever the bytes the shell
will receive type `sudo` at a command position. A different spelling of
the same key must not change that decision. Item 2 asks for production
code with production names, and no computed values that are thrown away.

## Root cause

`sudo_decision_text` keeps its own copy of the key names instead of
following the encoding the shell actually receives. `compose_input`
(`shell_input.rs:150`) already builds those bytes: text, then the encoded
keys, then `\r` when `enter` is set. Any key the parser treats as Space or
Enter but the copy does not recognise falls through as "types nothing".

Whatever approach is chosen, it must satisfy one constraint. Wherever the
bytes the shell receives contain a space, `\r` or `\n`, the decision text
must have a word break or a line break at the same point. One trap: in
bracketed-paste mode the text is wrapped in `ESC[200~ … ESC[201~` markers.
If the decision were taken on the raw bytes, the first word would be
`ESC[200~sudo`, which `command_has_sudo` does not see as `sudo`.
