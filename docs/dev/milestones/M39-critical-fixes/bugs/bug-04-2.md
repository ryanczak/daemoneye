# Bug 2 on phase-04: the copy's parent directory is created unsearchable, so the grant never matches

**Severity:** blocker
**Status:** open
**Filed:** 2026-11-23

## What's wrong

The architect ran `install-sudoers` live on pinky (sudo-rs 0.2.13) against
a throwaway script, `de-sudo-probe.sh`. The rule installed and parsed:

```
/etc/sudoers.d/daemoneye-de-sudo-probe.sh: parsed OK
Rule: matt ALL=(ALL) NOPASSWD: /usr/local/libexec/daemoneye/1000/de-sudo-probe.sh
root:root 440 /etc/sudoers.d/daemoneye-de-sudo-probe.sh
```

The grant did not work. As the user:

```
stat: cannot statx '/usr/local/libexec/daemoneye/1000': Permission denied
stat: cannot statx '/usr/local/libexec/daemoneye/1000/de-sudo-probe.sh': Permission denied
$ sudo -k; sudo -n /usr/local/libexec/daemoneye/1000/de-sudo-probe.sh
sudo: interactive authentication is required
```

A ghost's `sudo <name>` now resolves to a path the user cannot reach, so
every NOPASSWD script is broken. Before this phase they at least ran.

## What should happen

Every directory between `/usr/local/libexec` and the copy, meaning
`/usr/local/libexec/daemoneye` and `/usr/local/libexec/daemoneye/<euid>`,
ends up `root:root`, mode `0755`, whatever umask sudo applies. The copy
ends up `root:root 0755`. Running `sudo -n <copy>` as the user then works
with no password.

This must also repair a `daemoneye` directory that an earlier broken install
left at a restrictive mode. Re-running `install-sudoers` is the documented
fix, so it has to set the mode on directories that already exist, not just
on new ones.

## Root cause

`sudoers_install_steps` (`src/scripts.rs`) creates only the per-uid
directory with an explicit mode (`install -d -o root -g root -m 0755
/usr/local/libexec/daemoneye/<euid>`). `install -d` creates the missing
intermediate `/usr/local/libexec/daemoneye` itself, and `-m`/`-o`/`-g`
apply only to the directories named on the command line. The parent gets
`0777 & ~umask` under the command's umask, which sudo sets. On pinky that
came out unsearchable by the user. The `1000` directory being un-`stat`able
proves it, because statting an entry needs search permission on its parent.
sudo-rs then cannot resolve the command path for the invoking user, matches
no rule, and asks for a password. The spec named only `<euid>`'s directory,
so no test pinned the parent.

      comes before the rule step. `install_plan_copies_before_the_rule`, or
      a new plan test, asserts that both directories appear with `-m 0755`
      ahead of the copy. **The current plan names only the `<euid>`
      directory.** `install_sudoers` runs that same plan.

      passed.
