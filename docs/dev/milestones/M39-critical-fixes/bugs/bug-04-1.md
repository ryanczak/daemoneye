# Bug 1 on phase-04: new `unsafe`, a production `expect`, and an install plan that leaves out the rule

**Severity:** major
**Status:** closed (fixed by `46b490d3`, verified at review 2026-11-23)
**Filed:** 2026-11-23

## What's wrong

The sudoers fix itself is correct and tested. All four gates pass, and
the lib suite reports 3077 passed. Three things in `src/scripts.rs` break
`docs/dev/STANDARDS.md` or the phase's own acceptance criteria:

1. **(major) Two new `unsafe` blocks.** `root_script_path` (line 24) and
   `install_sudoers` (line 236) each call `unsafe { libc::geteuid() }`.
   STANDARDS §1 says: "No `unsafe` blocks. (If you think you need one,
   stop and report a blocker — `unsafe` requires principal-engineer
   review.)" The PE reviewed these and **declined them**, because a safe
   call already exists. `nix` is a dependency (`Cargo.toml`:
   `nix = { version = "0.31.3", features = ["fs"] }`), and
   `nix::unistd::geteuid() -> nix::unistd::Uid` is safe. It sits behind
   nix's **`user`** feature, which is not enabled yet. `Uid::as_raw()`
   gives the `u32`.
2. **(minor) A production `.expect()`.** `install_sudoers` (line 240) calls
   `root_copy.parent().expect("root_script_path always has a parent directory")`.
   STANDARDS §1 forbids `.expect()` in production paths.
3. **(minor) The install plan leaves out the rule.** The acceptance
   criterion asks for a test on the pure plan showing, in order, the
   directory, the copy, **and** the rule installed into `/etc/sudoers.d/`
   with mode `0440`, copy before rule. `sudoers_install_steps` returns only
   the directory and copy steps. The rule install happens later, inline in
   `install_sudoers`. `install_plan_copies_before_the_rule` asserts
   `plan.len() == 2`, so no test notices if the rule install moves ahead of
   the copy.

## What should happen

- No `unsafe` in `src/scripts.rs` outside its `#[cfg(test)]` modules. The
  effective uid comes from `nix::unistd::geteuid().as_raw()`, with `"user"`
  added to nix's feature list in `Cargo.toml`. The three older
  `unsafe { libc::geteuid() }` sites in `src/daemon/server/mod.rs` and
  `src/daemon/executor/shell_label.rs` are out of scope. Leave them.
- No `.expect()` or `.unwrap()` in the production part of
  `src/scripts.rs`. A missing parent becomes an error through
  `anyhow::Context`, or goes away because the directory is built
  directly rather than taken from `parent()`.
- The plan the tests see includes the rule-install step, and a test
  asserts all three steps in order: directory, then copy, then
  `install -m 0440 <rule temp file> /etc/sudoers.d/daemoneye-<name>`.
  `install_sudoers` must run the same plan the test checks. A separate
  hand-written sequence would make the test meaningless.

## Root cause

STANDARDS §1 forbids `unsafe`, but the executor copied an idiom from
`server/mod.rs` / `shell_label.rs` (`unsafe { libc::geteuid() }`) instead
of stopping to report a blocker. For the plan, the rule is written to a
per-PID temp file first, so the executor kept that step outside the plan
rather than passing the temp path in.
