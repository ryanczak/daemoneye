# Bug 1 on phase-01: mutation check 2 applied the inverse mutant and reports a red that cannot occur

**Severity:** major
**Status:** open
**Filed:** 2026-09-12

## What's wrong

§ Spec task 4, mutation 2, says: *"Make `uses_pty()` true only for the exact
value `"pty"`"* — that is `self.backend.trim().eq_ignore_ascii_case("pty")`.
The Update Log's `(mutation checks)` entry records patching it to
**`!self.backend.trim().eq_ignore_ascii_case("pty")`** — the inverse: true for
everything *except* pty.

Under that inverse mutant, `"ptty"`, `"tmxu"` and `""` all return `true`, so
`execution_invalid_value_falls_back_to_the_default` **passes**. The entry
nevertheless states:

> The invalid-value test **also** went red in the same run … `test result:
> FAILED. 0 passed; 1 failed`

Re-run at review with the entry's own mutant applied verbatim:

```
test config::tests::execution_invalid_value_falls_back_to_the_default ... ok
test config::tests::execution_tmux_is_the_only_opt_out ... FAILED
test config::tests::execution_backend_defaults_to_pty ... FAILED
test config::tests::execution_config_parses_from_toml ... FAILED
test result: FAILED. 2 passed; 3 failed
```

The invalid-value test is green; three *other* tests are red. The entry's
combined-run line (`1 passed; 1 failed`) already showed the invalid test
passing; the separate "0 passed; 1 failed" claim contradicts it and does not
reproduce.

The entry then concludes *"The separation the spec asked for did not hold."*
It did. With the mutation **as specified** applied at review:

```
test config::tests::execution_tmux_is_the_only_opt_out ... ok
test config::tests::execution_backend_defaults_to_pty ... ok
test config::tests::execution_config_parses_from_toml ... ok
test config::tests::execution_invalid_value_falls_back_to_the_default ... FAILED
test result: FAILED. 4 passed; 1 failed
```

Exactly the split the spec described: the invalid-value test alone is red and
the opt-out test stays green.

**The shipped code is correct** — every acceptance criterion holds, 92 config
tests, 1815 lib tests, all gates green. This bug is about the evidence artifact
and the false conclusion it draws about the spec.

## What should happen

`STANDARDS.md` § 1: a transcript must be mechanically captured, and a claim of a
test outcome must be the outcome that occurred. Mutation 1 in the same entry is
fine and stays. The mutation-2 entry must:

- show the mutant **as specified** (`eq_ignore_ascii_case("pty")` with no
  negation), and its real result — `4 passed; 1 failed`, the invalid-value test
  the only red;
- drop the claim that the invalid-value test went red under the inverse mutant,
  and the conclusion that the spec's separation did not hold.

The executor may keep a note that it first applied the inverse by mistake and
what that produced — that is an honest observation — but it must not stand as
the check's result.

## Root cause

A one-character inversion when applying the mutant (`!eq("pty")` for
`eq("pty")`), followed by a reported outcome that matches the *spec's
prediction* for the correct mutant rather than what the applied mutant
produced. The combined run in the same entry shows the true outcome
(`1 passed; 1 failed`) and was not reconciled with the separate claim.

value shown. All are scoped to the `(mutation checks)` entry —
`awk '/^### Update.*\(mutation checks/{f=1; next} /^### Update/{f=0} f'` on the phase doc — so the
criteria block cannot satisfy itself. *(The range skips its own heading line —

matches both patterns.)*
