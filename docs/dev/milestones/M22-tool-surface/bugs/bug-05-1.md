# Bug 1 on phase-05: the safety-property test asserts nothing

**Severity:** minor
**Status:** closed (fixed 2026-09-14, commit `3e0d4f0c`)
**Filed:** 2026-09-14

## What's wrong

`send_input_text_never_reaches_read_shell` is the test that pins this phase's
headline safety claim — *typed input is recorded for audit but can never be
surfaced by a read tool*. **Its second assertion cannot fail.**

`src/daemon/executor/knowledge/shell.rs`, in that test:

```rust
        assert!(
            !read_shell("s3", None, None, None).contains("SENTINEL-NOT-IN-OUTPUT"),
            "the read tools filter to \"o\" events, so typed text must never surface"
        );
```

**Demonstrated at review.** Replacing that assertion with a diagnostic panic
prints what `read_shell` actually returns:

```
DIAGNOSTIC read_shell returned: Error: no shell with id "s3" is in the registry.
No shells are live; call list_shells to confirm, or run a command first —
run_terminal_command creates a shell on demand.
```

The assertion holds because the reader never reaches a cast file at all. There
are **two** independent reasons, either of which alone makes it vacuous:

1. **Wrong registry.** The public `read_shell` reads
   `crate::shell::registry()` — the process-global — while the test's shell
   lives in a locally built `ShellRegistry::default()`. The lookup fails before
   any file is opened.
2. **Wrong directory.** Even with the registry right, the in-process host
   writes its `.cast` under the tempdir `spawn_with_cast` creates, whereas
   `read_shell` resolves `cast_path(id, started_unix)` under the test's
   `lifecycle_home()`. The test's own comment notices this split and concludes
   the read side is still being tested; it is not.

**Confirmed independently by mutation.** Making the cast reader stop filtering
input events —

```rust
    if array.len() != 3 || !matches!(array[1].as_str(), Some("o") | Some("i")) {
```

— at `src/shell/log.rs:263` leaves the test **green** (`1 passed`). That is the
exact defect the test exists to catch, and it does not catch it.

**The property itself is true.** `read_command_output` filters to `"o"` at
`src/shell/log.rs:263` and `read_shell_log` goes through it. Production
behaviour is correct; what is missing is the test.

**The test's first assertion is good and must be kept.** `find_stray_cast` +
`recorded.contains("SENTINEL-NOT-IN-OUTPUT")` genuinely proves the real
production path writes the `"i"` event through a real host. That half works.

## What should happen

The read-side assertion must reach a cast the reader can actually open, so
that breaking the `"o"` filter turns it red.

The two halves are testing different things and do not have to share a
fixture: *"the production path records the input"* needs a real host, while
*"a reader never surfaces an `"i"` event"* is a property of the reader over a
cast file and needs no host at all. The module already builds casts directly
(`CastWriter`, plus the hand-written `.meta.json` its `read_shell` fixtures
use) and already has a registry-injected reader seam, `read_shell_in`, which
is what makes a locally-built `ShellRegistry` reachable.

Whatever shape you choose, the DoD below is the test: the filter mutation must
turn it red.

## Root cause

Architect-side. The phase doc's Test plan item 5 specified the *scenario*
("send a distinctive string to a real host, then call `read_shell` and assert
the result does not contain it") and the acceptance criterion pinned only the
test's **name**. Neither could see that `read_shell` reads a different registry
and a different directory than the fixture populates, so a test that never
reaches the code under test satisfies both. This is the same failure shape as
`bug-04b-2` — a criterion pinning a name where the assertion's discriminating
power was what mattered — and it is the second occurrence in this milestone.

## Resolution — 2026-09-14

Fixed, and verified independently at review — twice, once before and once
after `bug-05-2`'s probe removal.

The repair took this doc's "split into two, say so" branch. The original test
keeps its name and its sound half — a real in-process host genuinely writes
the `"i"` event, asserted via `find_stray_cast`. The read-side property moved
to a new test,
`send_input_text_never_reaches_read_shell_in_a_reachable_cast`, which builds
its own `.cast` + `.meta.json` under the test's own `HOME` and reads through
the `read_shell_in` registry seam — closing **both** escape routes this doc
named (wrong registry, wrong directory).

**The DoD's load-bearing box, re-run at review with no probe in the tree:**
widening the shipped filter at `src/shell/log.rs:263` to
`!matches!(array[1].as_str(), Some("o") | Some("i"))` turns the new test
**red** —

```
thread '…::send_input_text_never_reaches_read_shell_in_a_reachable_cast'
  panicked at src/daemon/executor/knowledge/shell.rs:2865:13
test result: FAILED. 1 passed; 1 failed; 0 ignored; 0 measured; 1873 filtered out
```

— and reverting turns it **green** (`2 passed`). The `1 passed` in the red run
is the production-path half still passing, which is the shape this doc asked
for.

`knowledge::shell` → **44** (43 + 1, the announced split). Full lib suite
**1871**. The count change was explained in the Update Log, as this doc
required.
