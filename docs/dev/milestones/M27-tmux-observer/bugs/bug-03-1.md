# Bug 1 on phase-03: a presence connection that ends in an I/O error is never unregistered

**Severity:** major
**Status:** fixed (99f6a003)
**Filed:** 2026-10-10

## What's wrong

`handle_chat_attach` (`src/daemon/server/chat_presence.rs`) calls
`presence_register` and then runs three fallible steps, each with `?`:
sending the brief (`send_response_split(… SystemMsg …)`), sending `Ok`,
and the hold loop's `rx.read_line(…)`. `presence_unregister` and
`record_chat_detach` run only after the loop exits on a clean EOF. Any `Err`
returns early, so they never run.

The session's `CHAT_PRESENCE` count then stays ≥ 1 for the rest of the
daemon's life. Two things follow:

- `cleanup_pass` never evicts the session, because `presence_live` stays
  true.
- The detach is never stamped, so a later `chat --resume` gets no catch-up
  brief.

The trigger can be any of these:

- The client vanishes between the attach request and the reply.
- The client sends non-UTF-8 bytes, which makes `read_line` return
  `InvalidData`.
- The peer resets the socket. This becomes routine once phase 03b pushes
  alerts down this connection: a client that exits with an unread alert in
  its receive buffer resets the socket.

Separately (nit, same file set): `ask.rs` keeps a `_catchup_brief` tuple
slot that is always `None`. It also has a comment describing the code that
used to be there ("The N15 catch-up brief used to be sent here…"). Both are
dead leftovers of the deletion.

## What should happen

Phase spec, ChatAttach: "After that it holds the connection and reads until
EOF or error … **On close it unregisters.**" Every way the hold ends (EOF,
read error, or a failed reply write) unregisters exactly once. When that
connection was the session's last, it also stamps the detach.

## Root cause

The unregister is sequenced after the fallible steps rather than guaranteed
around them. `?` short-circuits past it.
