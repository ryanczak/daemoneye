# Bug 1 on phase-02: the scheduler's host shell is registered as sandboxed (`sandbox: Some("")`)

**Severity:** major
**Status:** open
**Filed:** 2026-10-09

## What's wrong

`run_script_on_host` in `src/daemon/scheduled.rs` runs the **host** path
through `ghost_sandbox::run_ghost_in_sandbox` with an empty sandbox name:

```rust
crate::daemon::executor::ghost_sandbox::run_ghost_in_sandbox(
    reg, owner, "", cmd, "scheduled",
    |shell_id| crate::shell::spawn_detached_host(shell_id, &[], 24, 80),
)
```

`run_ghost_in_sandbox` opens its shell through `shell_for_owner_in_sandbox`,
which records the shell with `sandbox: Some(sandbox)`. A plain host shell is
therefore registered as `sandbox: Some("")`.

## What should happen

A scheduled script on the host (`[sandbox] enabled = false`) runs in a
scheduler-owned PTY shell whose record has `sandbox: None`, like any other
host shell. The phase spec said to use the ghost path's host helper,
`run_ghost_remote` with `HostId::Local`.

## Root cause

`shell_marker_name` (`src/shell/session.rs`) returns `"sh"` for any record
whose `sandbox` is `Some`, because a sandbox's child is always `bash`. For a
host shell the child is the user's login shell. So the marker protocol picks
`sh`'s exit variable (`$?`) even when the login shell is fish or csh, which
need `$status`. For those users a scheduled script's exit code is garbage, or
the command never completes. It works on pinky only because the login shell
is bash. The record also wrongly claims the shell is sandboxed. Separately,
`run_script_on_host` computes an unused `_max_per_owner`.
