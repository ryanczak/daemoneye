# Bug 1 on phase-02: `PtyShell::run` does not enforce its timeout

**Severity:** major
**Status:** resolved (round 2, 2026-09-03, commit `014c877`)
**Filed:** 2026-09-03

## What's wrong

`PtyShell::run(&mut self, cmd, timeout)` accepts a `timeout` and returns
`Err` on expiry only if the command *emits output* often enough for a read to
return. A command that is silent past the deadline blocks in `read` and the
deadline is never reached.

Measured at review, against the committed tree, through the crate's own public
API (a throwaway crate with a path dependency on `daemoneye`):

```
timeout=2s  elapsed=20.1s  result=Ok(exit 0)
```

`run("sleep 20", Duration::from_secs(2))` returned **`Ok`** after **20.1
seconds**. The requested budget was 2 seconds. No error was returned and no
timeout was reported.

Second, independent evidence from a reviewer mutation. Making the end-marker
search nonce-agnostic (`src/shell/pty.rs`, `end_marker`) so that the real-PTY
test's marker never matches did **not** fail that test after its 10-second
timeout — it **hung the whole `cargo test --lib shell::pty::` run until a
10-minute external kill**. Four pure parser tests reported `FAILED`
immediately; `pty_bash_roundtrip_returns_real_exit_code` never returned.

## What should happen

Phase-02 § Spec, Task 5 states the contract:

> On timeout return an `Err` naming the timeout and the command; do not return
> a fabricated exit code.

`run` must return `Err` within a bounded margin of `timeout` **regardless of
whether the command produces output**. A silent command must not extend the
call past its budget.

This also has to hold for the test suite, per the standing project rule that a
starved read must fail fast rather than hang the run
(`docs/design/daemon-stalls.md`; the same class M8/M10 closed for the tty
tests). A future regression in this module currently hangs CI instead of
failing it.

## Root cause

`src/shell/pty.rs`, in `PtyShell::run`:

```rust
loop {
    let remaining = timeout
        .checked_sub(start.elapsed())
        .unwrap_or(Duration::ZERO);
    if remaining.is_zero() {
        return Err(anyhow::anyhow!(
            "timed out after {timeout:?} waiting for command output: {cmd:?}"
        ));
    }
    let read = self.reader.read(&mut chunk) ...;
```

`remaining` is computed and then used **only** for the `is_zero()` test; it is
never applied to the read. `self.reader` is the blocking master-side reader
from `try_clone_reader()`, so `read` parks until bytes arrive. The deadline is
therefore checked only *between* reads, and a command that writes nothing
produces no read to return between.

The mechanism is not a mistake in the loop's shape — the loop does what the
spec described. The spec named the required *behaviour* and did not name a
*mechanism* that can deliver it, which is the architect-side half of this bug
(recorded in the review verdict).

## Definition of done

- [ ] A named test `pty_run_times_out_on_a_silent_command` exists and passes.
      It spawns a real shell, calls `run` with a command that emits nothing for
      substantially longer than the budget (`sleep 20` is the measured case),
      and asserts **both** that the result is `Err` **and** that the elapsed
      wall time is under a bound comfortably below the command's own duration.
      Confirmed failing now: `cargo test --lib pty_run_times_out` reports
      `0 passed … 1550 filtered out`.
- [ ] The error returned on that path names the timeout and the command, per
      Task 5. The existing message text already does; it must actually be
      reached.
- [ ] `cargo test --lib shell::pty::` still reports `10 passed` or more with
      `0 failed`, and the whole run completes in **under 60 seconds** — the
      new test must not itself become the thing that stalls the suite.
- [ ] All four gates green: `cargo fmt --all`, `cargo build`,
      `cargo clippy --all-targets --all-features -- -D warnings`, `cargo test`.

**Constraint on the solution, not a prescription.** The fix must bound the
*read*, not merely the loop around it, and must not busy-spin the CPU while
waiting. `PtyShell` owns the master pty and its reader, so both a
readiness-based wait and a bounded blocking read are open; choose whichever
keeps `src/shell/` free of `unsafe` (STANDARDS.md §1) and free of
`.unwrap()`/`.expect()` in production paths (§2). Do not solve it by shortening
the real-PTY test's command so the case stops arising.

## Resolution — 2026-09-03 (round 2, commit `014c877`)

The blocking read moved off the `run` loop so the deadline is enforced whether
or not the command emits anything. Verified independently at review through
the crate's public API: `run("sleep 20", 2s)` returns `Err` at **2.0 s**
naming the timeout and the command, where it previously returned `Ok` after
20.1 s. Pinned by `pty_run_times_out_on_a_silent_command`, which still passes
after round 5's rework.

Round 2's fix introduced `bug-02-2` in the same area; that is resolved
separately and both are covered by tests now.
