# Bug 3 on phase-02: round 1's end-to-end evidence entry was rewritten with round 2's numbers

**Severity:** major
**Status:** resolved (architect, 2026-09-03) — restored from `3712c74`
**Filed:** 2026-09-03

## What's wrong

Round 2 added a correct new end-to-end entry — and then also **edited round
1's entry in place**, replacing its captured numbers with round 2's. The
round-1 entry now reports results the round-1 tree never produced.

From the round-2 commit `014c877`, the round-1 entry's captured lines (`-` is
what round 1 actually measured, `+` is what replaced it):

```
-test result: ok. 10 passed; 0 failed; ... finished in 0.07s
+test result: ok. 11 passed; 0 failed; ... finished in 2.00s
-test result: ok. 1546 passed; 0 failed; 4 ignored; ...
+test result: ok. 1547 passed; 0 failed; 4 ignored; ...
-fn wrap_command         (1): 3
-fn parse_outcome        (1): 7
-fn strip_markers        (1): 2
+pub fn wrap_command     (1): 1
+pub fn parse_outcome    (1): 1
+pub fn strip_markers    (1): 1
```

A line for `pty_run_times_out_on_a_silent_command` was inserted into round 1's
test list; that test did not exist in round 1. The server-authored `(complete)`
entry from round 1 was rewritten too.

The three deleted `fn …` counts were **the evidence that identified a defect in
the phase's own acceptance criteria** at the round-1 review. That record is now
gone from the document.

## What should happen

`docs/dev/WORKFLOW.md` § "End-to-end verification" is explicit:

> **One entry per dispatch, not per phase.** A phase that bounces and is
> re-dispatched needs a **new** end-to-end entry for the round that changed the
> code. An entry written in an earlier round does not carry forward: it
> describes a tree that no longer exists.

An Update Log entry is a **captured artifact of one dispatch against one tree**.
Later rounds append; they never revise. A superseded entry staying visibly
superseded is the point — the review reads the newest entry, and the older one
records what the earlier tree did.

Round 2's own new entry is correct and complete, and satisfies the requirement
on its own. Nothing was gained by editing the old one.

## Root cause

A deliberate consistency edit. The round-2 completion summary states it: "The
prior server-authored entry's Summary was updated to reflect the bounce
outcome." The same reasoning was applied to round 1's captured artifact.

The impulse — make the document internally consistent — is reasonable for
prose and wrong for evidence. Nothing in the phase doc said the Update Log is
append-only, so this is an architect-side gap in the round-2 notes as much as
an executor error, and it is recorded that way in the review verdict.

## Resolution — 2026-09-03 (architect)

Restored by the architect rather than the executor, and taken out of the
phase's executor scope. Round 3 spent its **entire 60-turn budget** on this
task — `git show`, `diff`, `sed` and `python3` against the phase doc, over and
over — and hard-failed on a `NoProgressStall` having never opened
`src/shell/pty.rs`. The empty diff and zero files changed are in that run's
`PhaseResult`.

Two reasons it does not belong to the executor:

- **Shape.** Splicing a 198-line block out of an old commit back into a file
  that has changed around it is exact text surgery. The executor cannot use
  `sed -i`, `perl -i` or `>` redirects into a file, so it must land the edit
  through `patch` with exact context — and this bug doc gave it none. That is
  an architect-side task-shape defect, of the same family already folded into
  `WORKFLOW.md` for mutation pairs.
- **Value.** It is record-keeping on the architect's own document. It produces
  no model-vs-spec telemetry, and the architect can do it with `git show` in
  one step.

Restored verbatim from `3712c74` (round 1's e2e entry through its
server-authored `(complete)` entry, 198 lines), with a superseded note added
above the block. Round 2's entries were not touched.

Verified: `grep -c '^fn parse_outcome        (1): 7'` returns 1, the round-1
entry again reports `10 passed` and `1546 passed`, and round 2's entry still
reports `11 passed` with `pty_run_times_out_on_a_silent_command`.

**The criterion in § Definition of done above was itself defective** and is
corrected in the phase doc: written unanchored, it matched the criterion's own
quoted text in the acceptance-criteria section and returned **2**, so it could
never have been satisfied as stated. The anchored `^fn …` form returns 1.
