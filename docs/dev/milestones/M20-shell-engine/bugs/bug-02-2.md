# Bug 2 on phase-02: `run` corrupts the shell's reader, so every second command fails

**Severity:** blocker
**Status:** open
**Filed:** 2026-09-03

## What's wrong

The round-2 timeout fix moved the blocking read onto a worker thread, but the
reader is never restored on the **success** path. The result is that a
`PtyShell` — the module's central object, designed to be long-lived and to run
many commands — fails on every second command.

Measured at review through the crate's public API, on a healthy shell with no
timeout anywhere involved:

```
six sequential commands on ONE healthy shell, no timeouts involved:
  run1: Ok  out="ok1"
  run2: ERR PTY closed while running "echo ok2"
  run3: Ok  out="ok3"
  run4: ERR PTY closed while running "echo ok4"
  run5: Ok  out="ok5"
  run6: ERR PTY closed while running "echo ok6"
```

The pattern is deterministic, and the error message is false: the PTY is open
and the shell is healthy. `echo ok2` **did execute** — only its output was
lost.

A second, related symptom: after a genuine timeout the shell stays poisoned
while the timed-out command keeps running, because the detached worker still
holds a live reader clone and competes for the same byte stream.

```
--- AFTER ONE TIMEOUT: same three runs ---
  run1: 5.0s Err(timed out after 5s waiting for command output: "ec)
  run2: 5.0s Err(timed out after 5s waiting for command output: "ec)
  run3: 5.0s Err(timed out after 5s waiting for command output: "ec)
```

Each of those three commands ran in the shell; each reported a timeout. **A
command that executes while the caller is told it timed out is the dangerous
shape here** — a later phase's agent would be free to retry a non-idempotent
command it had in fact already run.

## What should happen

A `PtyShell` must run commands sequentially and indefinitely. Every `run` on a
healthy shell returns that command's own output and exit code, whatever
happened on the previous `run` — success, timeout, or error.

This is the module's whole purpose: the milestone design
(`docs/dev/milestones/M20-shell-engine/README.md`, and
`docs/design/daemoneye-2.0.md` § 2.1) is one long-lived shell per owner
running many commands, with phases 06 and 07 building directly on that.

"PTY closed" must be reported only when the PTY is actually closed.

## Root cause

`src/shell/pty.rs`, `PtyShell::run`. `take_reader` installs a placeholder in
its place:

```rust
let mut reader = std::mem::replace(reader, Box::new(std::io::empty()));
```

The three exit paths do not treat that placeholder alike:

- **Timeout** → `drop(rx); drop(reader_handle); self.refresh_reader()?;`
- **`Disconnected`** → `self.refresh_reader()?;`
- **Success** → `drop(rx); drop(reader_handle);` and **returns without
  `refresh_reader()`**:

  ```rust
  if let Some(outcome) = parse_outcome(&buf, &nonce) {
      drop(rx);
      drop(reader_handle); // worker finished once it delivered the end marker
      return Ok(outcome);
  }
  ```

So after a successful `run`, `self.reader` is still `std::io::empty()`. The
next `run` hands *that* to `take_reader`; the new worker reads `Ok(0)` at once,
breaks, drops its `tx`, and the loop sees `RecvTimeoutError::Disconnected` and
reports "PTY closed while running". That branch *does* re-seat the reader,
which is exactly why the following command succeeds — hence the alternating
pattern.

The post-timeout symptom has a different mechanism in the same area: on
timeout the worker is detached while still holding a **live clone** of the
master's reader. `refresh_reader` adds a *second* live reader on the same
master; the two then race for bytes, and whichever wins consumes them. The
comment `// worker will exit on its own once the shell writes or dies` is
accurate about the thread's lifetime and silent about the fact that it keeps
consuming the stream until then.

**Why the suite missed both:** every test in `src/shell/pty.rs` spawns a fresh
`PtyShell` and runs exactly **one** command. Nothing exercises a second `run`
on the same shell, so the module's primary use is untested.

## Definition of done

- [ ] A named test `pty_runs_many_commands_on_one_shell` exists and passes: on
      a single `PtyShell`, at least **four** consecutive `run` calls each
      return `Ok` with that command's own distinct output and exit code.
      Confirmed failing now: no such test exists
      (`cargo test --lib pty_runs_many_commands` reports `0 passed`), and the
      behaviour it pins currently alternates Ok/Err.
- [ ] A named test `pty_shell_is_usable_after_a_timeout` exists and passes: a
      `run` that times out is followed by a `run` on the **same** shell that
      returns `Ok` with the right exit code and output, without waiting for the
      timed-out command to finish. Confirmed failing now: no such test exists.
- [ ] `pty_run_times_out_on_a_silent_command` still passes — the round-2
      timeout fix must be preserved, not reverted.
- [ ] `cargo test --lib shell::pty::` reports `0 failed` and completes in under
      60 seconds.
- [ ] All four gates green.

**Constraint on the solution, not a prescription.** The reader's ownership must
be well-defined across every exit path of `run`, and a timed-out command must
not leave anything behind that consumes the shell's byte stream. Note that two
live readers on one master is itself the hazard — re-seating a clone while a
detached worker holds another does not isolate them. A single long-lived
reader owned by the shell (rather than one taken and abandoned per `run`) is
one shape that satisfies this; choose whatever keeps `src/shell/` free of
`unsafe` and free of `.unwrap()`/`.expect()` in production paths. Do not fix it
by making the tests spawn a fresh shell per command — that hides the defect
rather than fixing it.
