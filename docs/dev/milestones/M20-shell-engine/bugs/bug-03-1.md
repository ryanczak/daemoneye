# Bug 1 on phase-03: a dangling UTF-8 carry leaks across a command boundary

**Severity:** major
**Status:** open
**Filed:** 2026-09-03

## What's wrong

When a command's output ends mid-character — which is exactly what phase-02
measured a 4096-byte PTY read doing — the carried bytes are **not** written
before the command's end marker. They are prepended to the *next* command's
first output event instead.

The result: the finishing command loses its last character's bytes, and the
next command's slice is polluted with them. Measured at review through the
crate's public API:

```
command 0 wrote bytes [65, 66, 228]   (A, B, and the first byte of a 3-byte char)
  read back cmd0 = "AB"
  read back cmd1 = "<U+FFFD>ZZZ"      (it had written only "ZZZ")

raw file:
  {"version":2,"width":80,"height":24,"timestamp":0}
  [1, "o", "AB"]
  [1.1, "m", "end 0"]
  [2, "o", "<U+FFFD>ZZZ"]
```

`read_command_output` for command 0 returned `AB`, dropping the third byte;
for command 1 it returned a replacement character followed by `ZZZ`.

## What should happen

The phase's own headline test states the guarantee: `read_command_output`
returns "exactly that command's own output bytes and nothing from its
neighbours." A command whose output ends mid-character must still read back as
its own bytes, and must not contribute bytes to its neighbour's slice.

Concretely, a carry outstanding when `mark` is called has to be resolved
*before* the marker line is written, so it lands inside the byte range the
index will attribute to the finishing command.

## Root cause

`src/shell/log.rs`. `mark` does call `flush_carry`, and `flush_carry` is
**vacuous** — it can never flush anything:

```rust
    fn flush_carry(&mut self) -> Result<()> {
        if !self.carry.is_empty() {
            self.write_output(Duration::ZERO, &[])
        } else {
            Ok(())
        }
    }
```

`write_output(_, &[])` re-enters `write_event`, which builds
`buf = carry + []` = the carry itself. The carry is only ever populated on the
`error_len().is_none()` branch, so it is by construction an **incomplete**
sequence starting at a character boundary. `std::str::from_utf8(&buf)`
therefore returns the same error with `valid_up_to() == 0`, the emitted text is
empty, `text.is_empty()` returns early, and the carry is written back
unchanged. The function is a no-op on every input that can reach it.

The completion summary states the opposite — that the flush was "fixed" and is
"covered by the existing `cast_carries_a_split_multibyte_character` test."
Neither holds: nothing is flushed, and that test never calls `mark`.

## Definition of done

- [ ] A named test `cast_flushes_a_dangling_carry_before_a_marker` exists and
      passes: write output ending mid-character, call `mark`, then write a
      second command's output, and assert via `read_command_output` that the
      first command's slice contains **all** its own bytes and the second
      command's slice contains **only** its own. Confirmed failing now — no
      such test exists (`cargo test --lib cast_flushes_a_dangling` reports
      `0 passed`), and the behaviour it pins is currently wrong.
- [ ] `flush_carry` (or whatever replaces it) demonstrably resolves an
      outstanding carry. A reviewer mutation that neuters it must fail the new
      test — if the test still passes with the flush removed, the guard is
      vacuous in the same way the current code is.
- [ ] `cast_preserves_ansi_and_unit_separator_bytes` no longer hardcodes
      `first_byte: 45`. That offset lands **inside** the 51-byte header line,
      and the test passes only because `read_command_output` skips the
      resulting malformed partial line — so it does not currently verify any
      byte range. Take the offset from `byte_len()` as the other tests do.
      Confirmed now: `grep -c 'first_byte: 45' src/shell/log.rs` returns 1.
- [ ] `cargo test --lib shell::log::` reports **12 or more** passing with
      `0 failed` (11 today plus the new test).
- [ ] `cargo test --lib shell::pty::` still reports `13 passed`.
- [ ] All four gates green.

**Constraint on the solution, not a prescription.** Resolving the carry means
deciding what those bytes *are* once no more input is coming for this command —
they cannot be completed, so they must be emitted rather than held. Whatever
shape you choose, the byte the writer accepted must end up inside the
finishing command's range, and the next command's slice must be untouched. Do
not solve it by making `mark` drop the carry silently: that loses a byte the
caller handed over, which is the same data loss in the other direction.
