# Bug 1 on phase-04: `annotated()` collapses cursor-positioned column layout

**Severity:** major
**Status:** resolved (round 2, 2026-09-03, commit `d952fd4`)
**Filed:** 2026-09-03

## What's wrong

`annotated()` drops every grid cell that has no contents, including cells in
the **middle** of a row. Terminal programs lay columns out by moving the cursor
rather than by writing spaces, so any column-aligned output loses its
alignment in the view the model reads.

Measured at review through the crate's public API, on a 40-column screen:

```
1) spaces written as literal characters:
   contents()  = "NAME      SIZE      MODE"
   annotated() = "NAME      SIZE      MODE"     <- fine
2) columns laid out with cursor-forward (ESC[nC):
   contents()  = "NAME      SIZE      MODE"
   annotated() = "NAMESIZEMODE"                 <- collapsed
3) coloured text positioned with ESC[nG:
   contents()  = "         failed"
   annotated() = "[ERROR: failed]"              <- leading trim, intended
```

Case 2 is the defect. `contents()` renders the row correctly because the grid
holds the gap; `annotated()` throws it away. `ls`, `top`, `git status`,
`docker ps` and most table renderers position columns exactly this way, so an
agent reading their output through `annotated()` sees run-together text.

## What should happen

Phase-04 § Spec, Task 4 point 4 states the rule:

> Trailing blank cells at the end of a row are not emitted as whitespace; a
> row's text is right-trimmed.

**Trailing.** An interior blank cell is part of the row's visible text and must
be emitted as a space, so that `annotated()` preserves the same column
positions `contents()` does. Right-trimming still removes the trailing run.

## Root cause

`src/shell/screen.rs`, in `annotated_row`:

```rust
            let cell = match self.parser.screen().cell(row, col) {
                Some(cell) => cell,
                None => break,
            };
            if !cell.has_contents() {
                continue;
            }
```

`continue` skips the cell entirely, so a gap contributes nothing to the span
buffer and the characters on either side become adjacent. The distinction the
spec draws — interior blanks kept, trailing blanks trimmed — is not made
anywhere: `flush_span` already right-trims via `span_buf.trim()`, so emitting a
space for a blank cell would have produced the specified behaviour on its own.

## Definition of done

- [ ] A named test `screen_preserves_cursor_positioned_columns` exists and
      passes: feed a row whose columns are positioned with a cursor-forward
      escape (`ESC[nC`) rather than literal spaces, and assert `annotated()`
      holds the same column positions as `contents()` for that row.
      Confirmed failing now — no such test exists
      (`cargo test --lib screen_preserves_cursor` reports `0 passed`), and the
      behaviour it pins is currently wrong.
- [ ] Trailing blanks are still trimmed: the existing
      `screen_trims_marker_text_and_drops_empty_runs` pair must keep passing,
      and a row with trailing gap must not gain trailing spaces.
- [ ] **`screen_does_not_merge_a_colour_run_across_a_row_boundary` is
      corrected to the case the spec named.** It currently feeds red on row 0
      and *green* on row 1, so the colour change alone forces a split and the
      test cannot discriminate the same-colour case its name claims. The spec
      asked for "a red run that reaches the last column of one row and
      continues at column 0 of the next … two separate `[ERROR:` markers, not
      one." Confirmed at review: the behaviour is already correct — feeding
      `ESC[31mabcdefgh` at 4 columns yields
      `"[ERROR: abcd]\n[ERROR: efgh]"` — but no test exercises it.
- [ ] `cargo test --lib shell::screen::` reports **11 or more** passing with
      `0 failed` (10 today plus the new test).
- [ ] `cargo test --lib shell::pty::` still reports `13 passed` and
      `cargo test --lib shell::log::` still reports `12 passed`.
- [ ] All four gates green.

**Constraint on the solution, not a prescription.** Whatever shape you choose,
`annotated()` and `contents()` must agree on column positions within a row,
and a blank cell must not silently vanish from between two visible characters.
Do not fix it by removing the right-trim — trailing gaps still go.

## Resolution — 2026-09-03 (round 2, commit `d952fd4`)

`annotated_row` now pushes a space for a cell with no contents instead of
skipping it, so an interior blank contributes to the row's layout while
`flush_span`'s trim still removes the trailing run.

Verified independently at review: columns positioned with a cursor-forward
escape render as `"NAME      SIZE      MODE"`, matching `contents()`, where
they previously collapsed to `"NAMESIZEMODE"`. A trailing gap still produces
no trailing spaces, and a fully blank row is preserved as an empty line.

The boundary test was corrected to the same-colour case the spec named, and
that correction was load-bearing: mutation-checked at review, merging rows now
fails it, which the round-1 red/green fixture could not detect.

**One residual, carried rather than re-bounced.** A gap sitting between a
coloured run and plain text is still lost — `"red      plain"` annotates as
`"[ERROR: red]plain"` — because those blanks join the open colour span and are
trimmed with it. This bug's own definition of done asked for `annotated()` and
`contents()` to "agree on column positions within a row", which is
**unachievable in general**: the marker text itself shifts every column after
it. Where a gap belongs relative to a marker is a design question for
phase-07, the first consumer that shows this text to a model. Recorded in the
milestone README's Notes.
