# Bug 1 on phase-10: the run is not pinned when nothing was picked, and an unparseable `shell` value now runs instead of being refused

**Severity:** major
**Status:** open
**Filed:** 2026-11-15

> Already approved, do not redo: the red bold input box and its corners, the
> `ToolCallPrompt.shell_label` field, `shell_label.rs`, `reusable_shell_for_owner`,
> the client title and fallback, the glyph changes, the docs, and the mutation
> and end-to-end evidence. Gates are green: fmt, build with 0 warnings, clippy,
> and `cargo test` passed=3025 failed=0.

## What's wrong

In `dispatch_foreground::dispatch` (`src/daemon/executor/dispatch_foreground.rs`),
`run_shell` is built from the pick:

- `Some(id)` → the id (correct);
- `None` → the caller's `shell` argument only when it is literally `"new"`,
  otherwise `None`.

That `None` has two consequences:

1. **The run is not pinned when nothing was picked.** With no `shell` argument
   and no idle shell, the prompt is labelled `…:new`, but the run gets
   `shell: None`. `None` re-runs the reuse rule after approval. A shell that
   was busy at prompt time and finished while the prompt was open is then
   reused, so the command lands in `s3` under a panel titled `matt@pinky:new`.
   Phase task 6 requires the run to get `"new"` when the pick is `None`.
2. **An unparseable `shell` value is no longer refused.** For `shell: "bogus"`,
   `pick_shell_for_run` returns `None` because `ShellId::parse` fails, which
   makes `run_shell` `None`. The command runs in the session's default shell.
   Before this phase, `resolve_shell_target` refused it with
   `Error: unknown shell target "bogus". …`, and nothing ran.

## What should happen

- The run's `shell` argument is the picked id, or `"new"` when the pick is
  `None`. The label and the run can then never disagree.
- An unparseable `shell` value is refused with `resolve_shell_target`'s own
  wording, and nothing runs. It is refused **before** the prompt, as a
  malformed `host` already is, because a value that can never be a shell is
  not a decision to put to the user. The refusal sends its `ToolResult` the
  same way the malformed-host refusal does.

## Root cause

`pick_shell_for_run` folds "explicitly new", "nothing idle" and "unparseable"
into the same `None`. `run_shell` then cannot tell them apart, so it passes
through only the literal `"new"`.
