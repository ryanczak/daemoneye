# Bug 1 on phase-01: chat attach fails whenever an alert is firing

**Severity:** blocker
**Status:** fixed (phase-01 rework, 2026-11-13)
**Filed:** 2026-11-13

## What's wrong

1. **The attach reply sends `AlertState` before `Ok`.** In
   `src/daemon/server/chat_presence.rs` (the `held` block of the
   `ChatAttach` handler), a non-empty registry sends
   `Response::AlertState` after the optional brief and *before*
   `Response::Ok`. The client's `attach`
   (`src/cli/commands/chat_presence.rs`) accepts exactly "zero or one
   `SystemMsg`, then `Ok`". Any other first frame hits
   `other => anyhow::bail!("unexpected chat-attach reply: …")`, and a
   frame other than `Ok` after a brief hits "unexpected chat-attach reply
   after the brief". So while any alert is firing, every `daemoneye chat`
   starts without its presence connection. The chat logs a warning and
   carries on, but gets no pushes, and its shells are never closed on
   detach. An always-firing deadman alert, the very case issue #3
   describes, makes this permanent. The spec said "after the `Ok`".
2. **`presence_broadcast_in` now writes invalid frames.** The push channel
   carries serialized frames, and the hold loop writes each one as it is.
   But `presence_broadcast_in(map, msg)` (`src/daemon/session.rs`) still
   sends the raw `msg` text. Its only remaining caller is a test, but it
   is a `pub` seam that puts a non-JSON line on the wire.
3. *(Minor.)* The new `tests/hygiene_allowlist.txt` entry for
   `tests/integration.rs` says "phase-02a's client work is expected to
   shrink it". Phase 02a does not touch that file. The entry should state
   the real reason (the gate-order tests) and nothing more.

## What should happen

- At attach, the daemon sends the optional brief, then `Ok`, then the
  `AlertState` frame when the registry is non-empty, on the held
  connection. The existing client parks the connection after `Ok`, and its
  parked task ignores non-`SystemMsg` frames, so this order needs no client
  change.
- Every frame a presence connection carries is a serialized `Response`.
  No public function pushes raw text.

## Root cause

The snapshot send was placed beside the brief, inside the reply, instead
of after the reply's `Ok`. Neither test drove the client's real `attach`
parser against the frame order the server produces.
