## What's wrong

The acceptance criterion says: remove the `skip_to_future` call from the
`Every` arm of `recover_interrupted`, then
`recover_interrupted_skips_a_running_every_job_to_its_next_slot` must fail.
The executor ran that mutation and the test stayed green (its own Update Log,
2026-11-15 02:36):

```
test scheduler::tests::recover_interrupted_skips_a_running_every_job_to_its_next_slot ... ok
test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 2893 filtered out; finished in 0.04s
```

The `panic!` probe that replaced it only shows that the test body runs. It
does not show that the test can detect a missing `skip_to_future`.

## What should happen

The test must pin the case issue #9 is about. `deadman-watchdog` was left
`Running` with its fired slot **many intervals** in the past, because the
daemon was down for six days. Recovery must still land on a future slot.
With `skip_to_future` removed, `advance()` alone moves the job one interval
forward, which is still in the past, so the test must fail.

## Root cause

`src/scheduler.rs:1094`: the test's fired slot is `Utc::now() - 10s` with a
300 s interval. One `advance()` already lands 290 s in the future, so the
`skip_to_future` loop never runs and removing it changes nothing the test
observes.
